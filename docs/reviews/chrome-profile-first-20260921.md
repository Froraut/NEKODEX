# Existing Chrome profile first

User requested reuse of an already signed-in Google Chrome profile, with selection before authentication and a new profile only when none matches.

The selected NEKODEX account now receives a native profile picker before Chrome passkey capture. It reads only Chrome Local State profile names/emails and validates existing profile directories. Saved per-account choices are preferred only while directory and email still match; the user can choose another profile. Labels such as Prim2 are never treated as account identity. Launch uses Chrome's normal executable with an exact profile-directory argument and no remote-debugging flags, copied profile, modified application or password/keychain access. Missing/denied/malformed metadata does not silently create a temporary profile. Explicit None matches retains the existing isolated login path; Firefox remains isolated.

Existing profile selection opens ChatGPT in that profile and waits for explicit Import after sign-in. Chrome's supported debugging-consent flow remains required for importing into NEKODEX; opening Google/Chrome alone is not ChatGPT authentication. Captured first-party cookies are checked in a disposable in-memory Electron session against the selected email before the existing account partition is touched. Mismatch/unknown identity refuses import and cleans up. The normal embedded verification remains required after installation. Existing Chrome is never terminated by this workflow. No token, cookie or authentication-response text is logged or placed in profile bindings.

Four focused tests passed: safe metadata/matching, cancellation/new-profile routing, isolated identity validation and duplicate-account rejection, exact directory selection and remembered choice. Existing account handoff and safe passkey UI checks passed; launcher TypeScript and renderer build passed. The first selection test accidentally used the real process-launch boundary before dependency injection was installed; corrected to inject launch and verified subsequent tests perform no browser action. No full authentication success is claimed by fixtures. The OS notification in the user's screenshot is not treated as authorization to bypass app-management protections.
