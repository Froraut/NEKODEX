# NEKODEX implementation wave 2 of 3, lane 16 — launcher state

Baseline: `3740505b0107af9a83053fd523ae1ad30be36465` (`3740505`). The working tree includes the uncommitted wave-1 changes. Exclusive source scope for this lane was `launcher/electron/state.cjs`; the requested review covered its direct state-publication contract and the accepted triwave cross-scope findings. No tests, typecheck, scripts, runtime/browser actions, production actions, or commits were run.

## Disposition

No additional source change is warranted in `launcher/electron/state.cjs`.

The current uncommitted wave-1 diff already supplies the state-side corrections:

- `update()` clears `codexCatalogVerified`, `codexPickerConfirmed`, and `mcpSetupComplete` whenever the committed state says `coreSetupComplete: false`. A later positive patch cannot restore those three readiness flags while core setup remains false.
- `update()` invalidates `mcpSetupComplete` when `browserInteractionMode` actually changes. The new mode is retained, while proof from the previous mode is no longer presented as current.
- `invalidateAccountProof()` clears account-bound MCP and browser-smoke proof in one persisted update. The caller-owned account selection, logout, and selected-account check paths can use the same atomic state-side contract.
- The exported invalidation patches keep the field set centralized without changing connector identities, public tool names, schemas, or ABI data.

## Residual cross-scope findings

The accepted late-writer findings are caller-side ordering problems, not state-store merge problems:

- T3-16-1 remains in `main.cjs`: `browser-smoke` must capture and re-check a runtime/configuration or proof epoch around `browserHost.smokeTest()` before publishing a positive result after connector migration invalidates smoke proof.
- The T2-16-1 MCP verification path already has the wave-1 `main.cjs` account-proof generation and currentness check. Its correctness depends on that caller check; `state.cjs` cannot infer which asynchronous verification operation produced a positive patch.
- The T1/T2 setup-core stale-read path remains in `main.cjs`; changing the state merge logic cannot make the pre-await `setupState` snapshot current after `probeAuthentication()` returns.
- Account selection, logout, and selected-account connector-check failure require their existing `main.cjs` callers to invoke `invalidateAccountProof()`. Adding an unused state API would not wire those transitions.

Adding a generic state epoch or compare-and-swap method in this exclusive file would be an optional API redesign unless the positive writers were changed to carry and validate its token. Automatically rejecting positive smoke or MCP patches would also reject legitimate fresh verification because the state store has no operation identity or completion context. Neither change is justified in this lane.

## ABI and remaining limits

`Native4`, `Native4DEV`, `ZeroRisk4`, their connector identities, public schemas, tool names, and ABI pins remain unchanged. The state store still cannot prove account-side connector approval, browser DOM behavior, live timing, or an atomic transaction against an external process. This lane performed focused manual source review only; no live race reproduction or executable verification was performed.
