## Confirmed repeat: T2-1-1

The wave2 candidate remains source-valid but is not a new wave3 path.

A pre-existing launchd definition can be byte-different from the plist generated by the persisted Full config while remaining loaded or installed and unchanged before setup. The setup snapshots those bytes, and the unchanged guards at `src/setup.ts:687-718` allow this baseline when there is no concurrent edit. If a later setup step fails, rollback restores the captured bytes at `src/setup.ts:884-886` or `:932-935`, then re-installs the prior loaded service with `installService(existing)` or `installTunnelService(existing)`. Those installers generate their definitions from `existing` and can overwrite the restored divergent bytes (`src/service.ts:116-132`, `src/tunnel-service.ts:112-133`). A legitimate custom launchd setting in the original definition can therefore be lost during recovery.

This is the same concrete trigger/consequence as `T2-1-1`: an initially divergent baseline, followed by a setup failure, with no concurrent edit required. It must not receive a `T3` ID. The minimum correction direction remains preserving the captured original definition through re-bootstrap, or refusing an unverifiable divergent baseline before mutation while retaining the existing concurrent-edit and unknown-state guards.

## Cross-scope adversarial checks

1. **Service rollback plus tunnel rollback.** The two rollback branches retain independent snapshots and status gates. A service recovery failure does not prevent the later tunnel branch from attempting to restore its own files, and the fallback handles tunnel-client/runtime-key cleanup only when the validation runtime is no longer active. No additional source root beyond the divergent-baseline repeat was established.

2. **Launcher-owned handoff.** The launcher can remove the old terminal-owned service and tunnel service before committing the launcher-owned configuration. On a later failure, the same original-definition restoration path is used. This increases the impact surface of T2-1-1 but does not create a separate trigger or consequence; the definition is still divergent before this setup and is overwritten by the recovery installer.

3. **Codex route/integration commit.** `installCodexIntegration` uses its own recovery journal and compensated multi-file write transaction (`src/codex-integration-shared.ts:361-430`). A failure in that final commit can be followed by setup rollback of config, service, tunnel, key, profile, and client state. I found no new cross-scope loss path in the inspected code. External edits are guarded by the integration transaction's expected-data checks and by setup's snapshots.

4. **Service and tunnel status uncertainty.** Initial and post-transition status probes are treated as failure-closed. Unknown service/tunnel state prevents unsafe restoration or reports manual recovery. The status checks are repeated in the service and tunnel branches but do not produce a distinct new path.

5. **DEV setup versus production setup.** Direct DEV setup refuses an existing Full tunnel whose stopped state cannot be established, then checkpoints its own config, profile, client, and key mutations. The stopped-observation-to-first-mutation interval remains a distributed ownership race documented in wave1. No new loss mode was demonstrated.
