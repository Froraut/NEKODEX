## Findings

### 1. [P1] The DEV catalog-error state is rendered as fully model-connected

- **Observed rendering:** in `06-setup-catalog-error.png`, the dominant “Next step” card says **“Models connected · tools not connected”**, offers **“Open workspace”**, and the “Model connection installed” row has a green completed check and disabled **“Done”** action. The same fixture is explicitly named `catalog-error`; its visible account and optional reply checks are green, so the model-connected claim is the decisive readiness signal rather than a generic page title. A user can reasonably leave Setup believing the Codex model layer succeeded.
- **Source inference:** the DEV path treats installation alone as model readiness. `pickerReady` becomes true whenever core setup is complete and `devProfile` is true, without requiring `codexCatalogVerified` or picker confirmation (`launcher/src/App.tsx:1501-1504`). That value drives the completed Setup row (`launcher/src/App.tsx:1636-1644`). `setupNextStep()` also skips both catalog verification and picker confirmation whenever `development` is true, then returns `ready` (`launcher/src/setup-progress.ts:3-14`); `ready` maps to the visible “Models connected” title and “Open workspace” action (`launcher/src/App.tsx:1573-1589`, using `launcher/src/i18n.ts:276-280`). This is stronger than “installed”: it asserts the downstream Codex layer is connected despite the fixture's failed catalog layer.
- **Trigger and user impact:** core installation completes in the isolated DEV profile, but the subsequent catalog request fails or remains unverified. Setup converts that partial state into “connected” and routes the primary action away from diagnosis. The likely impact is false readiness: the user opens the workspace, then encounters missing models with no explanation at the point where Setup declared success.
- **Precise fix:** keep **installed**, **catalog observed by Codex**, **picker confirmed**, and **tools verified** as separate status facts in DEV as well as production. If DEV intentionally cannot require picker confirmation, use a DEV-specific state such as **“Model connection installed · catalog not verified”** and a primary **“Open connection checks”** or **“Retry catalog check”** action; do not use “Models connected,” a completed green row, or “Open workspace” until the evidence required for that exact claim exists. The recovery action must inspect/retry the current isolated DEV route only. It must not sign into another account, change the selected account, rename a connector, install tools, or cross the normal/DEV profile boundary.

### 2. [P1] Overview visually prioritizes an installed-state success card over the active catalog failure, and the error has no direct recovery action

- **Observed rendering:** in `02-overview-degraded.png`, the largest, highest-contrast card says **“Model connection installed”** and uses the large NEKODEX cat mark. The connection list separately says **“Waiting for Codex”**, while the only explicit failure is a bottom-corner toast: **“Something went wrong — Codex reached NEKODEX, but loading the model catalog failed (HTTP 502; catalog).”** The toast can only be dismissed. “Continue setup” is available, but its label does not say that it opens routing checks or retries the failed layer. “Runtime Ready” in Recent events further increases the visual weight of success even though model discovery is degraded.
- **Source inference:** every failed operation except `mcp-verification` is copied into one global `error` string (`launcher/src/App.tsx:255-268`, `296-298`) and rendered outside the current surface through the generic `ErrorToast` (`launcher/src/App.tsx:408`). The toast uses a generic title, raw/localized message, and **Dismiss** as its only control (`launcher/src/App.tsx:3081-3093`). The source already has more useful layer-specific guidance — the catalog body says Codex reached NEKODEX, the catalog request failed, and the user should inspect Activity/routing details (`launcher/src/i18n.ts:15-16`) — but that guidance is not represented as a persistent inline state in the affected model-connection area. The toast correctly uses `role="alert"`; screenshots cannot establish focus behavior or screen-reader announcement quality.
- **Trigger and user impact:** a catalog operation fails after route reachability or core installation has succeeded. The page simultaneously communicates installed, waiting, runtime ready, and failed, with the strongest visual signals attached to the first three. Dismissing the toast removes the only explicit layer diagnosis. The user may retry setup, reinstall, or investigate ChatGPT sign-in even though the observed failure belongs specifically to model-catalog loading.
- **Precise fix:** promote catalog failure into the model-connection card/list as a persistent **Error** state: **“Codex reached NEKODEX, but the model catalog failed (HTTP 502). Your installed connection was kept.”** Make the adjacent action **“Open routing checks”** and place an optional **“Retry catalog check”** only where it can retry that layer without changing account, connector, approval, or installation state. Keep the global alert for immediate announcement, but make it secondary and link/focus the affected inline status rather than leaving Dismiss as the only action. Preserve the cat identity in the card; pair it with an error/status treatment so the brand mark does not function as an accidental success badge.

## Healthy recovery behavior observed

`12-update-error.png` gives the clearest layer and safety result of the three captures. It names the operation (“Update couldn't finish”), states the immediate failure (“The network connection was interrupted”), states the retained outcome (“The previous app is still installed”), keeps the installed version visible, and offers a user-controlled check rather than implying an automatic retry or restart. The copy also preserves account/settings and package-verification expectations (`launcher/src/update-copy.ts:3-14`). This is good recovery hierarchy in the synthetic fixture. It does not prove that a live interrupted update rolled back, that the previous app remained runnable, or that account/settings preservation was verified.

## Specific polish recommendations

1. **Use the existing “Try again” label for a displayed update failure.** The copy table defines `retry` (`launcher/src/update-copy.ts:8`), but the error-state screen renders the generic check action because the error state has no install button and the remaining button always uses `check` (`launcher/src/Updates.tsx:28-38`). When `failure` is present, label that safe recheck **“Try again”**; retain “Check for updates” for idle/up-to-date states.
2. **Expose an update failure phase only from typed state.** If the backend can provide `checking`, `downloading`, `verifying`, `installing`, or `rolled-back`, render a short heading such as **“Download interrupted · installation not started”** above the recovery sentence. Do not infer the phase or “app unchanged” guarantee from a free-form error string. This keeps network, package trust, replacement, and rollback as visibly separate layers.

## Subjective preference and evidence limits

Subjectively, the restrained purple palette, generous spacing, persistent sidebar version, and cat marks preserve NEKODEX's identity well across all three screens; the recommendation is to change status hierarchy and recovery wording, not the brand system. The low-contrast secondary text appears intentionally quiet, but contrast ratios, keyboard order, focus placement after an alert, zoom/reflow, reduced-motion behavior, and assistive-technology names were not verified from static PNGs. All account names and states shown are synthetic fixtures. No real account data, approvals, connector actions, catalog request, update, rollback, or installed-runtime behavior was observed.
