## Important findings

### 1. P1 — Arrow keys on the model-profile info control can change the selected profile

**Observed rendering.** None of the three assigned captures opens the custom
model-profile popup, so there is no screenshot claim about its open appearance or
live focus behavior.

**Source observation.** `handleRadioGroupKeys()` handles every arrow/Home/End event
that bubbles to a radiogroup and then focuses and clicks a radio
(`launcher/src/App.tsx:68-80`). `ZeroRiskModelMenu` attaches that handler to the
whole panel (`launcher/src/App.tsx:2622-2626`) while placing a separately focusable
information/tooltip control inside the same radiogroup
(`launcher/src/App.tsx:2662-2671`). The handler does not require the event target or
active element to be a radio. If focus is on the info control,
`radios.indexOf(document.activeElement)` is `-1`, so any handled key resolves to a
radio and calls `.click()`.

**Failure trigger.** Open the model-profile popup, Tab to the Pro-profile
information icon, then press an arrow key, Home, or End. The key intended to move or
inspect focus can activate a profile choice and close the popup. This is especially
important because the choice changes model behavior and can affect account usage;
keyboard navigation must not become implicit approval.

**Precise fix suggestion and ownership.** The renderer keyboard owner should make
the radiogroup handler return unless `event.target` is one of that group's enabled
`[role="radio"]` elements. Better, move the info control outside the radiogroup's
interactive subtree and associate its explanatory text with the Pro radio through
`aria-describedby`. Keep arrow-key selection for an actually focused radio, and
keep Enter/Space as the explicit activation path for the information control. This
is source-derived and remains unverified in a live keyboard/AT session.

### 2. P2 — Escape bypasses the dialog's busy lock and can hide an in-flight setting change

**Observed rendering.** In `17-context-dialog.png`, the dialog presents a toggle
and Close action. The synthetic fixture shows focus on Close and does not depict a
busy or applying state.

**Source observation.** The shared modal hook closes unconditionally on Escape
(`launcher/src/App.tsx:115-120`). `BiggerContextRecommendation` disables both the
switch and visible Close button while `busy` is true
(`launcher/src/App.tsx:3163-3173`), but it passes the same unrestricted `onClose` to
`useModalFocus()` (`launcher/src/App.tsx:3143-3144`). The asynchronous change sets
the busy flag before calling the backend and clears it only after settlement
(`launcher/src/App.tsx:838-848`).

**Failure trigger.** Toggle Bigger Context, then press Escape while the operation is
pending. The disabled Close button communicates that dismissal is temporarily
blocked, yet Escape closes the dialog. The operation continues; the user can
reasonably read disappearance as cancellation or completion even though neither was
established.

**Precise fix suggestion and ownership.** The dialog/focus owner should give
`useModalFocus` a `closeAllowed`/`requestClose` contract and ignore Escape while the
same condition disables Close, or allow dismissal consistently and project a
persistent applying/result status on the underlying Settings surface. Do not map
Escape to cancellation unless the backend exposes a real cancel operation. This is
source inference; pending Escape behavior was not exercised in live Electron.

## Specific polish recommendations

1. **Subjective preference, based on `14-settings-small.png`:** collapse the two
   interaction-mode cards to one column slightly earlier, using the workspace
   container width rather than only the app's compact-sidebar breakpoint. At 860 px
   the layout fits, but two narrow prose-heavy cards are slower to compare. Preserve
   the current card styling and cat identity; this is spacing/reflow polish.
2. **Subjective preference, based on `18-account-proxy.png`:** tighten the expanded
   proxy control group so the native select and Save button read as one labeled row,
   and use the existing chevron icon treatment for the Account pacing/Account proxy
   disclosures instead of literal triangle glyphs. Keep the warning copy adjacent
   and retain disabled Save until a deliberate value change.

## Evidence limits

The manifest's focused labels and screenshots confirm fixture state, not a complete
Tab order, focus-visible behavior after physical keyboard input, screen-reader
announcement, native select behavior, Escape behavior during a real asynchronous
operation, or focus restoration after every close path. No claim of full keyboard,
WCAG, runtime, account, or network verification is made.
