## Strengths

- The NEKODEX cat mark, name, DEV badge, dark palette, and lavender action color stay consistent across all three states. The product identity remains visible without competing with setup content.
- The page has a clear `h1`-level task, a prominent next-step card, ordered setup rows, and persistent account state in the sidebar. Green checkmarks make completed rows easy to scan.
- The new-user fixture states that the DEV browser, account, configuration, and runtime data are isolated. The catalog error is not silently swallowed: the toast is visible and `ErrorToast` uses `role="alert"` (`launcher/src/App.tsx:3081-3093`).
- Onboarding itself describes Manual mode honestly: the user pastes and sends the prompt and chooses connector, model, and effort (`launcher/src/App.tsx:501-508`; `launcher/src/i18n.ts:352-357`). The problem is loss of that context on the later Setup summary, covered below.

## Findings

### 1. High — The catalog-error state simultaneously claims model readiness and offers “Open workspace”

**Observed rendering.** In `06-setup-catalog-error.png`, the dominant next-step card says **“Models connected · tools not connected”** and its primary action is **“Open workspace.”** The same viewport shows an alert saying that Codex reached NEKODEX but loading the model catalog failed with HTTP 502. The completed rows and ready-colored checks visually reinforce success, while the only failure treatment is a detached bottom-right toast with **Dismiss**.

**Source inference.** DEV is explicitly exempted from catalog and picker gates in `setupNextStep()` (`launcher/src/setup-progress.ts:8-14`). `SetupSurface` likewise treats `coreSetupComplete` as picker-ready whenever `devProfile` is true (`launcher/src/App.tsx:1500-1512`), maps `ready` to the generic “Models connected” title and “Open workspace” action (`launcher/src/App.tsx:1573-1589`), and omits route diagnostics inside troubleshooting for DEV (`launcher/src/App.tsx:1656-1659`). The render is therefore consistent with the source conditions even though the messages conflict.

**Failure trigger and impact.** Trigger: the isolated DEV harness is initialized, but the latest Codex catalog request fails. The screen promotes workspace entry and labels the models connected before the failed catalog has recovered. A user cannot tell whether the error is ignorable DEV telemetry, a blocker for the requested task, or something that must be retried. This can turn a recoverable 502 into repeated workspace attempts or a false belief that Codex can already select the model.

**Precise fix suggestion and ownership.** The setup-progress/UI owner should model **profile initialized**, **catalog observed**, and **workspace usable** as separate facts. In this state, use a next-step title such as “DEV profile initialized · model catalog unavailable,” make **Retry catalog** or **View connection details** the primary recovery action, and show **Open workspace anyway** only as a secondary action when the DEV contract truly permits it. Add a DEV-safe diagnostic/retry body instead of hiding `RouteDiagnostics`. Do not clear the 502 merely because profile initialization is durable, and do not call the model connected until the catalog/picker layer has its own positive evidence.

**Unverified live behavior.** The fixture does not prove whether “Open workspace” would succeed, whether a retry is already available elsewhere, or whether the toast persists after navigation.

### 2. High — Manual DEV setup loses the recurring account and connector responsibilities selected during onboarding

**Observed rendering.** `15-manual-setup.png` contains no visible “Manual mode” label or recurring instruction. It says **“Models and tools are connected,”** tells the user to select NEKODEX in Codex, and labels the lower row **“MCP configured.”** Nothing on the summary says that Manual mode uses the selected account, requires the separate `Codex Zero Risk4` connector, or requires the user to select the connector/model/effort and send each prompt manually. The small gear beside “Model connection installed” is not enough to communicate the active interaction mode or those obligations.

**Source inference.** In `ContentSurface`, `devProfile` wins before `manualInteraction`, so Manual’s explanatory subtitle is discarded whenever both are true (`launcher/src/App.tsx:1593-1598`). The lower row also chooses `devMcpTitle`/`devMcpBody` solely from `devProfile` (`launcher/src/App.tsx:1662-1677`). The ready card reuses generic production copy regardless of interaction mode (`launcher/src/App.tsx:1573-1581`). This bypasses existing accurate Manual copy, including the separate connector and per-turn selection boundary (`launcher/src/i18n.ts:357,469-473`).

**Failure trigger and impact.** Trigger: the user selects Manual during onboarding and reaches the initialized DEV setup summary. The mode-specific explanation shown during onboarding disappears exactly when the user needs to act on it. The summary can be read as automatic availability, increasing the chance of using the wrong account or connector, forgetting the manual selection, or assuming that “MCP configured” means NEKODEX verified a live connector choice or tool execution.

**Precise fix suggestion and ownership.** The Setup/onboarding owner should compose DEV and interaction-mode state rather than choosing one copy branch. Keep the DEV isolation title, add a persistent **Manual mode** badge, and render a short recurring checklist: selected account, separate `Codex Zero Risk4` connector, choose connector/model/effort, paste/send, then confirm Sent. Qualify the completion language: “Manual tunnel credentials configured” and “Connector availability verified” only when each exact proof exists; retain the existing statement that a real task is required to confirm execution. Keep Codex sandbox/approval requirements explicit and do not imply that Manual mode inspects ChatGPT or approves commands.

**Unverified live behavior.** The fixture does not show a real Manual turn, account selector, connector picker, approval prompt, or tool execution. No claim is made that those live paths are broken.

### 3. Medium — The new-user screen gives the same sign-in action two competing hierarchies

**Observed rendering.** In `05-setup-new.png`, the top next-step card promotes **“Open sign in.”** Directly below, step 1 again offers **“Open sign in”** alongside the visually wider **“Use existing Chrome sign-in.”** The card describes the private embedded profile, while the row describes importing the currently signed-in Chrome account. A new user sees the same setup decision twice with different emphasis and must infer which path is recommended.

**Source inference.** For `nextStep === "sign-in"`, the next-step card always calls `openLogin()` and uses the embedded-login copy (`launcher/src/App.tsx:1573-1584`). On supported desktop platforms, the detailed row instead makes existing Chrome the main row action and embedded sign-in the secondary action (`launcher/src/App.tsx:1608-1623`). The two components therefore encode opposite action priority for the same state.

**Failure trigger and impact.** Trigger: Automatic mode, supported desktop platform, no authenticated launcher session. Users who follow the dominant top CTA may create or sign into the private launcher profile before noticing the existing-Chrome option. Users who prefer isolation may instead read the larger row action as the recommendation. This adds avoidable account-selection uncertainty at the first required step.

**Precise fix suggestion and ownership.** The Setup/onboarding owner should make one sign-in decision surface authoritative. Preferred option: keep the next-step card as a summary and place both account paths inside it with stable labels such as **Use existing Chrome session** and **Sign in to isolated profile**, each with one sentence explaining the account/profile effect. The step row can then show status and recovery rather than duplicate CTAs. If the detailed row remains authoritative, make the top CTA **Choose sign-in method** and focus/scroll that row instead of immediately opening a specific login path. Preserve explicit user choice; do not import or submit authentication implicitly.

**Unverified live behavior.** The screenshots do not establish which option users prefer, whether Chrome import requests a separate consent screen, or whether focus moves correctly after either action.

## Specific polish recommendations

1. **Observed structural polish:** completed setup rows still render their status inside disabled button styling (`SetupRow`, `launcher/src/App.tsx:2542-2561`). In all three screenshots, labels such as “Signed in,” “Connection test passed,” and “Done” look like unavailable actions. Render non-interactive completion as a status chip/text paired with the green check; keep a real enabled button only for repeatable checks or repair. This is a clarity recommendation, not evidence of a broken action.

2. **Subjective visual preference:** keep the catalog alert’s confirmed `role="alert"`, but visually associate recovery with the failed setup state. Replace generic “Something went wrong” with a stage-specific heading such as “Model catalog unavailable,” add **Retry** or **Details**, and leave **Dismiss** secondary. The current bottom-right placement and low-emphasis dismiss-only treatment make the failure feel unrelated to the success card. Keyboard focus movement and announcement timing remain unverified.
