# Update transaction resilience review — code lane 02

Scope: manual review of `launcher/electron/update.cjs`, `update-worker.cjs`, `update-readiness.cjs`, and `runtime-install.cjs`, with only the direct startup/update callers needed to establish control flow. No source edits, automated checks, builds, CI, UI operation, network/account/auth activity, or child agents were used.

## 1. High — the old installation is committed away before the configured runtime is proven usable

**Observed:** `proveUpdateReadiness()` in `launcher/electron/update-readiness.cjs:36-45` runs only the candidate runtime's `--version` command and writes the readiness marker when stdout equals the package version. Its caller in `launcher/electron/main.cjs:1587-1593` emits that marker immediately after renderer loading. The production startup branch that upgrades persisted runtime configuration, starts the configured service, and reconnects the bridge route begins later and asynchronously at `launcher/electron/main.cjs:1681-1745`. Meanwhile `waitForReadiness()` accepts the marker at `launcher/electron/update-worker.cjs:284-303`, and `runTransaction()` commits and deletes the prior package at `launcher/electron/update-worker.cjs:341-343`.

**Failure trigger:** a candidate can load its window and print the expected version, then fail in `upgradeManagedRuntime()`, `startIfConfigured()`, or `connectBridgeRoute()` because its runtime/config contract is incompatible or its local service cannot become healthy. The updater has already committed, so the later recovery UI/route fallback runs from the new package and the previous application is no longer available for automatic rollback.

**Inferred impact:** a valid executable is treated as a usable candidate even when the configured local runtime cannot accept work. This is especially risky for a release that changes runtime/config schemas: the update is irreversibly accepted at the exact point where compatibility has not yet been exercised.

**Proposed fix and ownership:** the update lifecycle owner should replace the version-only proof with a structured, local readiness result. Keep `--version` as an identity field, but require the candidate startup coordinator to report readiness only after: (1) the installed bundle has passed `validateRuntimeBundle`; (2) a side-effect-free runtime self-check has loaded the real CLI entrypoint and critical modules; and (3), when a managed runtime is configured, the local supervisor reaches `ready` and its local health/control endpoint reports the expected release/config generation and accepts turns with zero active work. Do not make external ChatGPT authentication or a live model request part of this gate. Move marker creation behind that awaited startup result and have `waitForReadiness()` validate explicit `appVersion`, `runtimeBundleId`, `configGeneration`, and `healthStatus` fields rather than accepting a version string. Runtime/launcher owners supply the self-check and health evidence; the lifecycle owner owns the final marker and worker validation.

## 2. High — rollback is package-only; durable runtime and compatibility configuration are outside the journal

**Observed:** `buildJob()` in `launcher/electron/update.cjs:293-337` passes package paths and the current runtime executable to the worker, but no durable runtime/config generation or compatibility-state paths. `prepareTransaction()` in `launcher/electron/update-worker.cjs:88-166` creates operations only for the application target (or Linux wrapper/AppImage). Independently, candidate startup calls `ensurePackagedRuntime()` before readiness at `launcher/electron/main.cjs:1394-1410`; `ensurePackagedRuntime()` installs a new version directory under `coreHome/versions` in `launcher/electron/runtime-install.cjs:218-288`. The release migration that can rewrite managed runtime configuration and route state occurs in `upgradeManagedRuntime()` after the current readiness marker (`launcher/electron/main.cjs:1681-1717`; direct implementation at `launcher/electron/runtime.cjs:1466-1524`). `rollback()` restores only `transaction.operations` at `launcher/electron/update-worker.cjs:194-217`.

**Failure trigger:** once finding 1 is corrected by waiting for real runtime startup, the candidate may install its runtime and migrate `config.json`/managed route state, then fail a later local health or bridge check. Worker rollback restores the old application package, but the old app restarts against candidate-era configuration/route state and an unjournaled runtime installation. Today the too-early marker mostly hides this path by committing before migration; it does not make the transaction atomic.

**Inferred impact:** app, runtime, and config can identify different releases after a failed update. Restoring an entire user-data directory would also be unsafe because browser/session changes and unrelated user activity could be overwritten.

**Proposed fix and ownership:** the same lifecycle owner should introduce a small generation manifest shared by `update.cjs`, `runtime-install.cjs`, and `update-worker.cjs`. Before replacement, record the old app version, runtime bundle ID/path, config hash/generation, and only the launcher-owned route/integration records that migration may change. Stage the candidate runtime and migrated config as a new generation without switching the active generation. After the structured readiness proof, atomically commit the package plus the active-generation pointer; on failure, retain the old pointer and remove/quarantine only candidate-owned artifacts. For migration compatibility, treat installations without a generation manifest as generation 0, continue reading the existing `config.json`, and use compare-and-swap hashes when restoring legacy files so rollback never overwrites a file changed after the snapshot. Keep browser profiles, conversations, logs, and session state outside this rollback set. The runtime/config owner defines the exact launcher-owned files and a reversible migration; the update lifecycle owner performs the atomic switch and recovery.

## 3. Important — a replacement shutdown error aborts rollback before any package restore or old-app relaunch

**Observed:** the failure path in `runTransaction()` awaits `stopReplacement()` before calling `rollback()` (`launcher/electron/update-worker.cjs:344-350`). `stopReplacement()` deliberately throws when launch was authorized but child identity cannot be established on Windows (`launcher/electron/update-worker.cjs:251-258`), or when POSIX process-group ownership cannot be established while the group remains alive (`launcher/electron/update-worker.cjs:263-270`). Therefore those safety errors skip both `rollback(transaction)` and `launch(executableFor(old job))`. The guard/recovery path calls the same `stopReplacement()` first at `launcher/electron/update-worker.cjs:373-379`, so an unchanged ownership ambiguity can repeat rather than advance recovery.

**Failure trigger:** the supervisor dies or its process identity lookup becomes unavailable after launch authorization, while the replacement child/process group remains alive and then fails readiness. The worker cannot prove that it is safe to kill the process tree; its safety exception exits before restoring the package. The durable prior package remains in `.previous-*`, but the target and journal stay in an interrupted state until a later environment change makes recovery possible.

**Inferred impact:** this avoids killing an unrelated process, but it can strand the user on the failed candidate and turn an automatic rollback into a login/restart-dependent recovery. Repeated recovery launches can encounter the same ownership ambiguity.

**Proposed fix and ownership:** the update lifecycle owner should persist an explicit `rollback-pending-stop` phase before attempting shutdown. Add a candidate-owned shutdown handshake (transaction token plus candidate PID/identity) that asks the replacement to close admission, preserve its normal session state, stop its runtime, and exit; then verify exit before restoring files. If identity still cannot be proven, leave the old package and generation intact, keep the recovery registration, and retry with bounded backoff or at the next safe startup instead of falling out of the recovery state. Journal each attempted ownership observation so recovery is idempotent. Only after the recorded candidate is confirmed stopped should the worker restore the package/runtime/config generation and relaunch the old app. This keeps the current fail-closed process-kill rule while making the pending rollback a first-class recoverable state.

## Review limit

These are source-observed transaction/control-flow findings. Failure outcomes and user impact are inferred from those paths; no failure was reproduced. The review intentionally did not assess unrelated updater trust/download code, broad runtime behavior, or UI behavior.
