# UI review 05 — Browser navigation and tabs

## Scope and evidence

- **Image viewed:**
  `/Users/alex/.codex/visualizations/2026/09/19/01a0b97e-6ae2-77d2-bdeb-fef95c2acfa9/resilience-ui/16-browser-running.png`
- **Fixture metadata read:** the manifest identifies this as a 1360×960 English
  `browser-running` synthetic capture with `No active task` as the heading, no capture errors,
  no root overflow, and focus reported on the Browser navigation item.
- **Source inspected:** `BrowserSurface` in `launcher/src/App.tsx`,
  `launcher/src/browser-controls.ts`, browser state types and styles, and the direct native tab,
  navigation, viewport, and cancellation boundaries in `launcher/electron/browser-host.cjs`.
- **User goal:** understand which ChatGPT surface and Codex task is selected, move safely between
  tabs, and distinguish viewing/hiding a surface from cancelling a running task.

The Browser surface keeps the NEKODEX cat identity consistent without overwhelming the browser
chrome. The selected account remains visible above the tabs, the selected tab is visually distinct,
the address and zoom areas have a familiar order, and the native layer keeps background task views
alive outside the visible workspace instead of conflating selection with ownership.

## Findings

### 1. High — the hidden Home surface says “No active task” while two task tabs are visibly busy

- **Observed rendering:** `16-browser-running.png` shows Home selected, two additional synthetic
  task tabs with orange busy indicators, and the central heading `No active task`. Both toolbar and
  empty-state actions say `Open ChatGPT`. The screen therefore presents active work and denies it in
  the primary message at the same time.
- **Source evidence:** `BrowserSurface` renders the empty state whenever `visible` is false
  (`launcher/src/App.tsx:1378–1406`). For every authenticated Automatic-mode state it then selects
  `copy.noActiveTask` and `copy.noActiveTaskBody` (`1382–1389`), without checking
  `browser.tabs` for running/loading/testing tabs or whether Home is merely selected. The native
  boundary deliberately keeps non-selected running views alive offscreen
  (`launcher/electron/browser-host.cjs:1549–1605`), so hidden content and absent work are different
  states by design.
- **Trigger:** a user leaves Home selected or hides the embedded surface while one or more Codex Web
  turns continue in task tabs.
- **Specific fix:** derive the empty-state copy from tab activity as well as visibility. When work is
  active, use a heading such as `2 tasks running in the background`, body copy explaining that Home
  is selected and task tabs can be opened, and a primary action that selects the most relevant
  running tab and reveals its surface. Reserve `No active task` for the actual zero-active-tab case.
  Keep the cat mark and account label; they correctly anchor product and account identity.
- **Source inference:** selecting a task tab calls the native `selectTab`, which swaps the exact
  owned `WebContentsView`; this supports a direct “Show running task” action without changing task
  ownership. The synthetic capture does not prove how quickly the live view appears.

### 2. High — closing a running tab is presented as a small generic close action although it cancels the Codex turn

- **Observed rendering:** no close controls are visible in the resting screenshot, even though the
  two busy tabs are closable. Their only persistent state affordance is a 6px orange dot.
- **Source evidence:** every closable tab gets the same `Close tab` label and immediate
  `closeBrowserTab` call (`launcher/src/App.tsx:1288–1300`). CSS makes the button 18×18px and fully
  transparent until hover or keyboard focus (`launcher/src/styles.css:637–653`). At the native
  boundary, closing a tab whose status is `running` records user cancellation, calls
  `cancelTurn(traceId)`, and then removes the tab (`launcher/electron/browser-host.cjs:1718–1741`).
  This is a task-cancellation boundary, not a visual tab cleanup.
- **Trigger:** the pointer crosses a busy tab, the hidden × appears, and the user clicks it while
  intending only to dismiss or hide the browser view; keyboard users can also tab to a control that
  was visually absent before focus.
- **Specific fix:** give running tabs an explicit `Cancel task…` action with a minimum 28–32px hit
  area and status-aware accessible name such as `Cancel running task: <title>`. Require a compact
  confirmation/popover that states the Codex turn will stop, then show `Cancelling…` and disable
  repeated activation until the native cancellation settles. Completed/ready tabs may keep a
  non-destructive `Close tab` action. Hiding ChatGPT should remain the separate toolbar action and
  must never imply cancellation.
- **Unverified live behavior:** no live tab was closed, so this review does not claim whether another
  app-level confirmation currently appears outside the inspected direct call path.

### 3. Medium — tab state is color/motion only and is absent from the tab’s accessible name

- **Observed rendering:** the two task titles are truncated and both end in the same small orange
  dot. The title fragments suggest different situations (`checkin…` and `waiting…`), but the chrome
  itself does not state whether a tab is starting, actively running, waiting for user action, ready,
  failed, or cancelled.
- **Source evidence:** `browserTabTone` collapses loading/running/testing into one `busy` tone and
  error/aborted into one `error` tone (`launcher/src/App.tsx:3213–3217`). `StateDot` is explicitly
  `aria-hidden` (`3073–3075`), while the tab has `role="tab"` and `aria-selected` but no status in
  its label or description (`1255–1288`). CSS communicates status through a 6px green/orange/red dot
  and pulse (`launcher/src/styles.css:494–514`).
- **Trigger:** a user compares several concurrent tasks, uses a screen reader, cannot perceive the
  color difference, has reduced motion, or sees titles truncated before their distinguishing text.
- **Specific fix:** preserve the compact dot as a secondary cue, but add a localized status word to
  each tab’s accessible name/description and expose a short visible status on hover/focus or when
  the title is truncated. Keep cancellation/aborted distinct from provider failure. For states that
  need action, use explicit text such as `Waiting for you`; do not encode approval or account state
  in color alone.
- **Unverified live behavior:** the fixture contains only synthetic titles and tones; it does not
  verify real screen-reader announcements or transitions between native states.

## Polish recommendations

1. **Subjective preference:** remove the hover treatment from the read-only address capsule
   (`launcher/src/styles.css:720–723`) or make it perform a clear action such as copying the safe,
   formatted ChatGPT location. Its current hover border/background suggests an editable address bar,
   but `BrowserSurface` renders a non-interactive `div`.
2. **Subjective preference:** when the surface is hidden, keep one `Open ChatGPT` action in the empty
   state and rename the toolbar action to the selected target (`Show Home` or `Show <task>`), or omit
   it from the toolbar in that state. The duplicate labels compete without explaining which tab will
   be revealed.
