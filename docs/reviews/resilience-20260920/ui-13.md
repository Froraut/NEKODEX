# UI review lane 13: privacy and account UX

Manual review only. The assigned captures are synthetic Electron/React fixtures and contain no real account data. I inspected the rendered fixtures and the directly relevant renderer/DTO sources; I did not run the app, tests, builds, live UI, authentication, account APIs, or network requests, and I did not use child agents.

## Images viewed

1. `03-accounts.png` — Accounts, ready state, 1360×960 capture (manifest viewport 1360×928).
2. `18-account-proxy.png` — Accounts with Account proxy expanded, 1000×760 capture (manifest viewport 1000×728).
3. `06-setup-catalog-error.png` — isolated DEV Setup with catalog error, 1360×960 capture (manifest viewport 1360×928).

The cat mark, NEKODEX wordmark, muted violet palette, left navigation, and compact status chips remain visually coherent across all three screens. This review does not recommend changing that identity.

## Findings

### 1. [P1 privacy] Account identifiers are always exposed in the primary management and Setup views

- **Observed rendering:** `03-accounts.png` shows the complete email-like identity under every account name, including accounts that are not selected. `06-setup-catalog-error.png` repeats the selected identity in the completed sign-in row. The values are synthetic, but their placement demonstrates the normal rendering contract.
- **Source inference:** `AccountSettings` renders `account.accountLabel` verbatim in every card (`launcher/src/AccountSettings.tsx:94-97`), and Setup interpolates `browser.accountLabel` directly into its completed row (`launcher/src/App.tsx:1609-1616`). `AccountPoolSnapshot` models the identity as an unrestricted nullable string and supplies no display/privacy state (`launcher/src/types.ts:215-222`).
- **Trigger and impact:** screen sharing, a support screenshot, shoulder viewing, or a recorded demo exposes every signed-in account identifier even when the user only needs to show routing, readiness, or proxy settings. This is a concrete privacy risk in the rendered UI; whether every live provider label is an email address is unverified.
- **Precise fix:** keep the user-created local account name visible, but mask the provider identity by default in Accounts and Setup (for example, `r••••1@example.test`). Add one intentional “Reveal account identity” control scoped to the current screen, with an accessible label that states which account will be revealed; reset it when leaving the surface. Keep raw identities out of screenshots, exported diagnostics, notifications, and error text. The main-process DTO should expose a redacted display form by default rather than relying on every renderer call site to mask the raw label.

### 2. [P1 trust] “Replace credentials” does not identify which credential store or account surface will change

- **Observed rendering:** in `03-accounts.png` and `18-account-proxy.png`, “Replace credentials” is the strongest action on the selected account card. The page says each account has a saved login, but it does not say that this action opens the isolated ChatGPT browser profile, what is stored locally, or that it is separate from Codex CLI/Desktop authentication. The proxy disclosure is more precise: it explicitly says “this account’s browser only” and rejects embedded credentials.
- **Source inference:** the button first selects the local account, marks replacement state, opens the Browser surface, and calls `openAccountLogin(account.id)` (`launcher/src/AccountSettings.tsx:104-117`). The current renderer API has only this browser-account login operation and no quota or Codex device-login DTO (`launcher/src/types.ts:343-352`). By contrast, the new draft Codex controller describes its result as `shared-codex-auth-store`, reports whether CLI auth was saved, says the desktop account was not changed, and requires desktop identity confirmation (`launcher/electron/codex-login.cjs:185-207`). No Codex-login or official-quota UI is present in the reviewed renderer, so the native flow below is a planned requirement rather than a claim about an existing screen.
- **Trigger and impact:** a user who needs to refresh one account’s browser session can reasonably read “Replace credentials” as replacing a password, API credential, Codex CLI identity, or all authentication. Reusing this CTA for the draft device flow would erase the approval and account-binding boundary: browser-profile authentication is per account, while the draft Codex login targets a shared auth store and does not itself change the desktop identity.
- **Precise fix:** rename the current action to **“Open browser sign-in”** when unverified and **“Re-authenticate browser session”** when already verified. Add concise local-storage copy beside the action: “Saved in this account’s isolated browser profile on this Mac. NEKODEX does not store your password.” Build the future native flow as a separate **Codex CLI sign-in** panel, never as another state of this button. Before opening the device URL, show the pinned local account, the shared-store scope, and a user confirmation. During the flow show starting/waiting/cancelling/expired states and keep the pinned account visible. After completion, state separately: “CLI credentials saved,” “Codex Desktop account unchanged,” and “Confirm the displayed identity before using it.” A selection change or cancellation must visibly end the flow rather than silently rebind it.

### 3. [P1 state clarity] Setup presents “Models connected” and a successful installation while the current catalog request is failed

- **Observed rendering:** `06-setup-catalog-error.png` simultaneously shows the prominent next step “Models connected · tools not connected,” a green completed “Model connection installed” row with a disabled “Done” action, and an alert saying the model catalog failed with `HTTP 502; catalog`. “Open workspace” remains the primary CTA. The user cannot tell whether models are currently usable, merely installed, or unavailable until recovery.
- **Source inference:** in DEV, `pickerReady` becomes true whenever core setup is complete, regardless of current catalog evidence (`launcher/src/App.tsx:1501-1504`). That feeds the ready next-step title and Open workspace action (`launcher/src/App.tsx:1573-1605`) and marks the installation row complete (`launcher/src/App.tsx:1636-1644`). The global error toast only renders a generic title, raw message, and Dismiss action (`launcher/src/App.tsx:3081-3093`), so it does not alter the Setup hierarchy or route directly to diagnostics. The fixture proves this combination can render; it does not prove a live catalog request failed or that model execution is unavailable.
- **Trigger and impact:** a catalog request fails after installation state has been recorded. The durable fact “connection installed” and the current fact “catalog read failed” are both valid, but the UI turns the durable fact into the dominant current-health claim. A user may open the workspace expecting selectable models, dismiss the only warning, or retry installation even though the correct next action is catalog diagnosis/retry.
- **Precise fix:** represent installation and current availability as separate states. Keep “Model connection installed” as a durable completed row, but when the latest catalog receipt is failed, override the top card with **“Models could not be loaded”**, explain that installation remains intact, and make **“Review diagnostics”** or **“Retry model catalog”** the primary action. Include the HTTP status/reason in an expandable technical detail, not the only recovery text. The alert should offer the same direct action and preserve the privacy-safe diagnostics language already present in `routingCatalogFailureBody` (`launcher/src/i18n.ts:14-17`). Do not relabel the account, change credentials, or request broader approval as part of catalog recovery.

## Specific polish recommendations

1. **Bring the expanded proxy form back into the NEKODEX component language.** In `18-account-proxy.png`, the native fieldset border creates a large empty rectangle and the low-contrast “Save proxy” looks disabled even though `AccountProxySettings` does not disable it when the account is idle (`launcher/src/AccountProxySettings.tsx:12-29`). Use a borderless named form group, the existing settings input/button tokens, a responsive row, and an explicit unchanged/saved/invalid status. Enable Save only when the normalized draft differs from the saved proxy. Preserve the existing browser-only scope and embedded-credential warning.

2. **Remove redundant selection signals inside each account card.** The selected card currently uses a highlighted border, a “Selected” badge, and a disabled button also labelled “Selected.” Keep the border and badge; remove the disabled duplicate action and reserve that position for an available task such as “Select” on other cards. This is a subjective hierarchy preference based on the captures, not a functional or accessibility defect.

## Planned quota UI requirements

No official quota UI exists in the reviewed renderer, so the following are requirements for the parent’s future implementation, not findings against the current screen. Attach quota data to the account card whose browser session produced it; never merge it into the local activity counters. Show `fetchedAt`, coverage, and a clear **Unavailable** state with the reason and retry timing. Unknown fields remain unknown rather than zero. Additional buckets should be labelled as provider-reported and disclose truncation. Refresh results must remain bound to the same account/session evidence epoch before display. Do not display access tokens, token claims, cookies, raw session payloads, or provider responses.

## Evidence and accessibility limits

The three screenshots confirm visual hierarchy, visible copy, and the contradictory fixture state. Source review confirms the render paths and DTO distinctions. Keyboard order, focus restoration after disclosure/selection, screen-reader announcements, contrast ratios, responsive behavior outside the two supplied viewport sizes, live account labels, login cancellation, quota refreshes, and catalog recovery behavior were not exercised. The manifest reports no root overflow and identifies the focused surface/control, but that is fixture metadata rather than full accessibility verification.
