# UI review lane 04: multiple ChatGPT accounts

Manual review only. The audited surface is the Accounts page and its per-account
selection, sign-in/replacement, readiness checks, pacing, and proxy controls.
No source changes, tests, builds, live UI, real accounts, network calls, or child
agents were used.

## Evidence viewed

- `03-accounts.png` — synthetic Electron/React capture, Accounts ready scenario,
  1360 × 960 capture with a 1360 × 928 viewport. The first account is selected,
  authenticated, model-checked, and connector-checked with zero active tasks; the
  second account has two active tasks and an unchecked connector.
- `18-account-proxy.png` — synthetic Electron/React capture, Accounts ready scenario,
  1000 × 760 capture with a 1000 × 728 viewport. The selected account's proxy
  disclosure is expanded with the saved `System settings` value.
- Capture metadata explicitly marks both images `synthetic: true` and reports no
  capture errors (`resilience-ui/manifest.json:43-60,343-360`).

## Design language

- **Observed rendering:** The surface preserves the NEKODEX identity: quiet dark
  workspace, lavender cat/brand accent, restrained selected-card border, compact
  status chips, and card-contained account controls. Account identity and model/tool
  readiness are visually separate.
- **Source contract:** The page copy says each account owns a saved login, balanced
  routing uses checked accounts, tool work requires connector checking, and continuing
  tasks remain on their original account (`launcher/src/i18n.ts:217-235`). The card
  renders `enabled`, `authenticated`, `checked`, `connectorReady`, and `activeTurns`
  as distinct states (`launcher/src/AccountSettings.tsx:87-125`).
- **Governing owners:** `AccountSettings` owns routing, selection, login/replacement,
  and account checks. `AccountSafetySettings` and `AccountProxySettings` own the two
  expandable editors. `nekodex.css:275-296` supplies the account-card presentation.
- **Explicit exceptions:** No current surface-specific `DESIGN.md` was found. The
  captures are fixtures and do not prove API success, live authentication, actual
  account capabilities, proxy application, or active-turn preservation.

## Findings

### 1. High — a fully verified account loses the visible control that excludes it from new routing

**Observed rendering.** In `03-accounts.png`, the selected verified account shows a
checked but disabled **Use for new tasks** checkbox even though it has **Active tasks:
0**. The second, incompletely verified account exposes the same checkbox as editable.

**Source inference.** `locked` is defined as `verified && !replacing`, where verified
requires authenticated, account-checked, and connector-ready state
(`AccountSettings.tsx:89-92`). That predicate disables the enabled-account checkbox
(`:104-106`). It does not depend on active turns. Consequently the UI removes the
account-routing opt-out precisely after all checks succeed. The only local state that
unlocks it is `replacingId`, which is entered through **Replace credentials**
(`:107-113`), an unrelated and much stronger action.

**Failure trigger and consequence.** A user verifies an account, then wants to stop
assigning new work to it while preserving its saved login and any existing turns.
The card presents the correct routing control but makes it unavailable with no reason
or recovery action. This weakens the account boundary expressed by **Use for new
tasks** and pushes the user toward credential replacement to regain an ordinary
routing control.

**Precise fix and ownership.** The `AccountSettings` owner should remove `locked` from
the checkbox's disabled predicate. Disable it only for the actual pending mutation
(`busy`) and, if the backend requires one, a specifically represented account-state
constraint. Keep disabling an account distinct from sign-out or credential removal;
the card should continue to show that running/retained turns stay with their existing
owner. If changing the checkbox invalidates readiness evidence, show that consequence
next to the control before mutation rather than hiding the control.

**Unverified live behavior.** This review did not call `setAccountEnabled`; it does not
claim how a real running or retained turn behaves after the toggle.

### 2. High — the account-check lock is inverted relative to active-task eligibility

**Observed rendering.** In `03-accounts.png`, **Check account** and **Check connector**
are disabled for the fully verified account with zero active tasks. On the second
account, which visibly reports **Active tasks: 2**, those two actions are presented as
available while **Local tools: Needs setup** calls attention to checking the
connector.

**Source inference.** Both check buttons use `busy || manual || locked` and omit
`account.activeTurns` (`AccountSettings.tsx:116-117`). Thus successful verification
permanently disables a deliberate refresh, while an unverified account with active
turns remains actionable. The neighboring pacing and proxy editors use
`account.activeTurns > 0` as their lock (`:119-125`), establishing the page's own
active-task boundary. The rendered state and source therefore contradict each other
within one account-management task.

**Failure trigger and consequence.** Capability or connector availability changes
outside NEKODEX, or the user simply needs current evidence before balanced routing.
An idle previously verified account cannot be rechecked. Conversely, clicking check
on the visibly active second account can only rely on a later API rejection or risk
mixing inspection with active work. The page neither exposes the valid refresh nor
prevents the visibly invalid attempt.

**Precise fix and ownership.** The `AccountSettings` owner should use
`busy || manual || account.activeTurns > 0` for both check actions and remove `locked`
from that decision. Keep the same controls enabled for idle verified accounts, with
copy such as **Re-check account** and **Re-check connector** when evidence already
exists. For active accounts, retain the disabled controls and add one card-level
reason, for example **Finish 2 active tasks to check this account**, so one explanation
covers both buttons and the nested editors.

**Unverified live behavior.** No check was sent. The report does not claim whether the
mock API, Electron handler, or live ChatGPT account would accept or reject either
captured action.

### 3. Medium — pacing and proxy editors do not expose whether Save is meaningful or locked by active work

**Observed rendering.** `18-account-proxy.png` shows an expanded proxy editor whose
saved value is already **System settings**, yet **Save proxy** is still presented as
an action. The form sits inside a large default fieldset outline with no state label;
the surrounding copy says only to save while idle. In `03-accounts.png`, the account
with two active tasks still exposes both collapsed disclosures without any visible
lock explanation.

**Source inference.** `AccountProxySettings` synchronizes a draft from the saved proxy
but never compares them before rendering the submit button (`AccountProxySettings.tsx:8-26`).
The parent disables the whole proxy fieldset when `activeTurns > 0`
(`AccountSettings.tsx:123-125`), but the disclosure remains openable and receives no
lock reason. `AccountSafetySettings` has the same pattern: synchronized draft, always
present Save button, and a silently disabled fieldset (`AccountSafetySettings.tsx:13-40`).
Neither component distinguishes **unchanged**, **unsaved**, and **blocked by active
tasks**.

**Failure trigger and consequence.** With an idle account, the user cannot tell
whether Save will apply a change or redundantly recycle connections. With an active
account, opening either editor reveals disabled controls but does not explain what
must finish or whether the draft is retained. The generic proxy paragraph describes
policy but does not report the current editor state.

**Precise fix and ownership.** The `AccountProxySettings` and
`AccountSafetySettings` owner should derive `changed` from draft versus saved data and
receive an explicit lock reason from `AccountSettings`. Disable Save when unchanged;
show **Unsaved changes** only after an edit; when active turns lock the editor, show
the shared **Finish N active tasks to save changes** message inside the disclosure.
Use the existing NEKODEX control styling for a compact wrapping form row and remove
the browser-default fieldset border; this keeps the account card as the visual
container. Do not auto-save proxy or pacing changes, and do not clear account data or
interrupt active turns.

**Unverified live behavior.** The synthetic proxy capture proves presentation only.
No proxy, pacing policy, connection recycling, draft retention, or save result was
exercised.

## Polish recommendations

These are subjective preferences, not correctness findings.

1. Keep the selected badge in the card header and omit the disabled **Selected**
   button from the same card. `03-accounts.png` shows the status twice, and
   `AccountSettings.tsx:97,114-115` confirms both are rendered from the same
   `selectedId` condition. One status marker leaves more room for useful actions.
2. Replace the browser-default disclosure triangles with the existing NEKODEX
   chevron treatment and a full-width summary hit area. The current raw triangles in
   both captures look detached from the rounded card language; the cat mark, colors,
   and restrained motion should remain unchanged.

## Improve first

Fix finding 2 first. It has the clearest two-sided contradiction in the same capture:
the idle account cannot refresh evidence, while the account visibly running two tasks
offers that action. Correcting the predicate and adding one active-task reason improves
account checking, connector checking, and the nested-editor lock explanation without
changing authentication, native approval, connector identity, or ownership of active
turns.
