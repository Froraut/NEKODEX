## 1. High — one failure presentation hides whether the next action checks, downloads, or installs

**Observed rendering:** `12-update-error.png` shows “Update couldn't finish,” an interrupted-network message that says the previous app remains installed, and one primary action labeled “Check for updates.” The panel does not identify whether checking, downloading, verification, installation, or rollback failed, and it does not show the candidate version.

**Source inference:** `Updates()` collapses the external `error` prop and `state.status === "error"` into one `failure` and one title at `launcher/src/Updates.tsx:11-16`. The recovery action is nevertheless selected indirectly from the remaining state: `available + failure` renders “Try again” and invokes `onInstall` at `launcher/src/Updates.tsx:33-35`, while `error` renders “Check for updates” and invokes `onCheck` at `launcher/src/Updates.tsx:36-38`. The direct caller preserves the same distinction implicitly: recheck errors populate `updateError` at `launcher/src/App.tsx:629-644`, and install exceptions populate it at `launcher/src/App.tsx:793-805`. Users therefore see the same failure heading while “Try again” may authorize download/restart and “Check for updates” performs a read-only recheck.

**Failure trigger:** any update error, especially a network interruption during download versus a metadata/check failure. The screenshot wording sounds like an interrupted update, but its button routes through checking semantics. From the synthetic fixture alone, it is unverified whether this exact combination can occur in the live updater.

**Precise fix and ownership:** the update-state owner should expose a typed failure receipt with `phase` (`check`, `download`, `verify`, `install`, or `rollback`), `candidateVersion`, `recoveryAction`, and a backend-confirmed `previousVersionUsable` value. `Updates.tsx` should render phase-specific copy and an explicit action: “Check again,” “Resume download,” “Retry verification,” or “Retry download and restart.” A retry that can install/restart must say so and remain a user click; it must not be hidden behind generic “Try again.” Only state that the previous app is usable when the updater has provided that receipt. The UI owner implements the presentation after the lifecycle owner defines the receipt.

## 2. High — the busy workflow has no visible cancellation boundary or point-of-no-return

**Observed rendering:** `11-update-download.png` clearly shows version, bytes, total, speed, percentage, and the statement that NEKODEX will close and reopen automatically. There is no Cancel, Pause, or “safe to leave this page” action while the 169.8 MB transfer is in progress.

**Source inference:** `busy` renders progress at `launcher/src/Updates.tsx:27`, changes the helper copy to the restart promise at line 30, and suppresses the check action at lines 36-38. Once state leaves `available`, the install button is absent as well, so no update action remains. `UpdateProgress.tsx` displays the transfer but has no interaction contract. This can be reasonable during an irreversible swap, but the renderer does not distinguish cancellable download/verifying work from the installing/restart phase.

**Failure trigger:** a slow or stalled download, metered connection, accidental update choice, or a user who needs to defer the restart after the transfer has begun. Live cancellation support is unverified; the screenshot proves only that no control is rendered.

**Precise fix and ownership:** define an explicit backend phase boundary and expose `canCancel`. While downloading, provide “Cancel download”; cancellation should abort the transfer, retain only authenticated reusable cache data, and return to the available state without installing. If verification can be safely cancelled before worker handoff, allow the same action there. Once replacement begins, remove Cancel and show direct copy such as “Installation has started. NEKODEX will restart when it is safe.” Preserve the existing rule that active work blocks installation, and never turn a cancelled or retried download into implicit install/restart approval. The lifecycle owner supplies cancellability and acknowledgment; the UI owner renders the phase-specific control.

## 3. Important — assistive progress can disagree with the animated visible progress

**Observed rendering:** `11-update-download.png` presents a coherent determinate meter: 46.4 MB of 169.8 MB and 27.4% align visually. A static fixture cannot establish screen-reader announcements or animation timing.

**Source inference:** visible bytes and percentage use the smoothed `reading` and `fraction` at `launcher/src/UpdateProgress.tsx:48-58`, while `aria-valuenow` is calculated from the unsmoothed raw `bytes` at lines 53-54. For the 180 ms interpolation window after each observed update, assistive technology can receive the target percentage while sighted users see an earlier number and bar position. The mismatch recurs on every progress sample; it is not evidence that downloaded bytes are fabricated, because interpolation is correctly bounded to observed targets.

**Failure trigger:** any determinate download update while motion is enabled and the document is visible. Reduced-motion and hidden-document paths publish the target immediately, so this specific mismatch is transient or absent there.

**Precise fix and ownership:** derive `aria-valuenow` from the same smoothed `fraction` used by the bar and visible percentage, or keep the visual interpolation but announce a separately throttled observed reading in a dedicated polite live region. Use integer `aria-valuenow` plus `aria-valuetext` containing the same displayed bytes/total/percentage. During indeterminate verification or installation, omit numeric values and expose the current phase as text. This belongs entirely to the `UpdateProgress` UI owner.

## Specific polish recommendations

1. **Subjective preference:** use a warning/error glyph and restrained error tone in the failure state instead of retaining the purple download symbol. Keep the NEKODEX cat mark, typography, and lavender accent in navigation so the product identity remains intact; change only the local status semantics.
2. **Subjective preference informed by source:** make the helper/footer sentence state-specific. During download, say that verification happens before replacement; during verification, say that the package is being checked; after a confirmed rollback, say that accounts/settings and the prior version were preserved. The unconditional promises in `launcher/src/update-copy.ts:11-14` and `launcher/src/Updates.tsx:30,42` read well, but the synthetic captures cannot verify those outcomes.
