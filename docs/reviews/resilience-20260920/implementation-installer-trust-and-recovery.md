# Installer trust and recovery implementation

## Completed changes

- `scripts/install-launcher.sh` now accepts only the public NEKODEX repository identity. On macOS it requires the observed release publisher Team ID `CNMWGJF2CG`, bundle ID `dev.codexwebgpt.launcher`, a timestamped Developer ID signature, Gatekeeper acceptance, and the same Team ID on the embedded Bun runtime.
- The macOS installer now copies and validates the candidate in a hidden staging directory beside the final application, moves the existing app to a durable sibling rollback path, commits with same-filesystem renames, and keeps EXIT/signal recovery active until the final installed app and version have been revalidated. The temporary download directory no longer owns the only rollback copy.
- Linux AppImage installation now requires a preinstalled Node.js runtime and verifies `release-metadata.json` against the existing packaged NEKODEX Ed25519 public key before the AppImage is extracted, installed, or run. Repository, tag, version, timestamps, GitHub Actions provenance, asset name, size, and SHA-256 are bound. The downloaded AppImage is never used as its own verifier. Missing Node fails with an explicit dependency/trust error.
- `scripts/install-launcher.ps1` now accepts only the NEKODEX repository and requires a timestamped Authenticode signature whose thumbprint is in a source-controlled trusted list. The list is deliberately empty because the current Windows deliverable is documented as an unsigned preview; the standalone installer therefore fails before downloading anything. A future signed Windows release must first commit its real public certificate thumbprint through the normal reviewed trust-rotation path.

## Contracts and limits

- `checksums.txt` remains an accidental-corruption cross-check. Linux authorization comes from signed metadata; macOS authorization comes from the pinned native publisher identity. Windows unsigned previews remain outside the trusted installer and authenticated updater paths.
- The dependency-free macOS path does not bootstrap Node or execute a downloaded verifier. Linux can verify the Ed25519 policy only with a Node runtime that was already installed independently; this requirement is explicit and fail-closed.
- The embedded Linux public key and validity interval mirror `launcher/release-trust.json`. A future key rotation must update both the application trust policy and this standalone verifier in the same reviewed transition release. The macOS Team ID pin likewise requires an explicit reviewed update if the publisher identity changes.
- No source claim was found in `README.md:61-79` that the Linux AppImage supports a particular old distribution or GLIBC baseline. It says only `Linux x64`. No README change is needed. The current workflow step name overstates its evidence: parent may narrowly rename `Verify Linux AppImage ABI on current Arch` to `Check final AppImage libnotify and unresolved launcher symbols on current Arch`. Establishing an oldest-supported-distro claim would require the broader full-ELF/baseline CI work excluded from this worker scope.
- No update-worker/updater source, release workflow, README, CI, account state, or installed application was modified. No automated test, build, package, network request, credential access, live UI action, or child agent was run. Parent owns focused checks and integration.
