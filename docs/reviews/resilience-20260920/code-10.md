# UI/backend state-contract review — lane 10

Scope was limited to manual review of `launcher/electron/state.cjs`,
`launcher/electron/upgrade-readiness.cjs`, the proof/state projection in
`launcher/electron/main.cjs`, and the renderer contracts in
`launcher/src/setup-progress.ts`, `launcher/src/types.ts`, and
`launcher/src/Overview.tsx`. Direct callers were inspected only where needed to
establish a user-visible failure path. No source was changed and no automated
checks, builds, CI, live UI, account access, or network operations were run.

## 1. P1 — A normal launcher restart unconditionally discards valid connector proof

**Observed.** `currentRuntimeIdentity()` defines proof identity from the launcher,
daemon, and tunnel PIDs (`launcher/electron/main.cjs:169-173`), and
`ensureRuntimeProofCurrent()` invalidates persisted MCP proof whenever that PID
tuple differs (`launcher/electron/main.cjs:200-210`). A verified proof is persisted
with that transient tuple by both verification success paths
(`launcher/electron/main.cjs:834-836`, `launcher/electron/main.cjs:858-860`), while
`readState()` requires the tuple for persisted `mcpSetupComplete` to survive
deserialization (`launcher/electron/state.cjs:145-156`). Production startup then
explicitly calls `invalidateAccountProof()` before starting the configured runtime
(`launcher/electron/main.cjs:1682-1686`, `launcher/electron/main.cjs:1740-1742`).
The upgrade-preservation branch cannot repair this: `preserveSetup()` requires the
current state's contract (`launcher/electron/upgrade-readiness.cjs:14-16`), but it is
called after invalidation has cleared that contract and identity
(`launcher/electron/main.cjs:1685-1691`).

**Failure trigger.** Verify the connector successfully, quit NEKODEX cleanly, and
open the same installation with the same account/configuration. The previous PID
tuple cannot equal the newly started runtime tuple, and startup also clears proof
before evaluating upgrade preservation. The UI therefore reports local tools as
unverified and asks for verification again even though no semantic setup identity
changed.

**Proposed fix and ownership.** The lifecycle/state owner should split durable proof
identity from transient runtime-instance health. Persist proof against
`SETUP_CONTRACT + setupIdentity + connectorName` (and, if needed, a stable runtime
configuration/release digest), then validate the newly started process separately
through supervisor ownership/health. Preserve the pre-invalidation proof snapshot
through startup/upgrade, compare it only after the replacement runtime and account
identity are known, and invalidate only on a semantic mismatch or failed health
check. `setupRuntimeIdentity` should either become transient and non-persisted or be
replaced with a stable generation generated by the configuration owner. The same
lifecycle owner should change `main.cjs`, `state.cjs`, and
`upgrade-readiness.cjs` together.

## 2. P1 — Manual mode is simultaneously “complete” and permanently “needs setup”

**Observed.** The app shell defines manual interaction setup as complete once
`coreSetupComplete` is true, without catalog or picker proof (direct caller
`launcher/src/App.tsx:583-610`). The two reviewed renderer contracts disagree:
`setupNextStep()` applies production catalog and picker gates to manual mode
(`launcher/src/setup-progress.ts:8-14`), and `Overview` defines model/workspace
readiness solely from `codexCatalogVerified && codexPickerConfirmed`
(`launcher/src/Overview.tsx:16-19`). It consequently renders the model connection as
pending and routes the primary action back to Setup
(`launcher/src/Overview.tsx:24-35`). This is not just wording: the navigation gate
and next action use different readiness predicates for the same state.

**Failure trigger.** Configure a production Manual-mode runtime and local tools so
`coreSetupComplete` and tool proof are true, while no automatic Codex model-catalog
receipt/picker confirmation exists. The shell removes the required Setup badge, but
the Setup summary asks for catalog/picker work and Overview says setup is unfinished;
its primary button returns to Setup instead of opening the workspace. Inference:
because Manual mode deliberately keeps connector selection as a per-turn manual
step, those automatic catalog/picker facts may never arrive, so the contradictory
state can persist indefinitely.

**Proposed fix and ownership.** The renderer state-contract owner should define one
shared selector, for example `interactionReadiness(state, profile)`, and use it in
the shell, `setupNextStep`, and `Overview`. For production Manual mode, readiness
should require the Manual contract actually promised by the backend (installed core,
configured/healthy local tools, and any explicit Manual verification), while catalog
and picker proof should gate Automatic mode only. Keep “models ready” and “tools
verified” as separate facts rather than folding both into a generic ready boolean.
The backend owner should confirm the intended Manual contract; the renderer owner
should then replace all three duplicated predicates in one coupled change.

## 3. P2 — A catalog failure is projected as a volatile operation and can remain stale after recovery

**Observed.** The catalog monitor turns a failed receipt into a global failed
operation (`launcher/electron/main.cjs:245-260`) but persists no catalog failure
identity/status in launcher state. On success it sets only the verified/restart
booleans and emits a resolving operation only when the single global
`lastOperation` still happens to be that catalog failure
(`launcher/electron/main.cjs:267-279`). Any intervening operation can overwrite
`lastOperation`. The direct renderer subscriber stores every non-MCP failed operation
in its global error channel but does not clear that channel on a completed operation
(`launcher/src/App.tsx:255-267`). Thus even the conditional completion event is not a
reliable inverse of the earlier failure.

**Failure trigger.** Let a current runtime return a failed model-catalog receipt so
the monitor publishes `catalog-verification: failed`; then let a later catalog
request succeed. The state can advance to `codexCatalogVerified: true`, while the
failure banner remains. If any other operation was published between failure and
success, the backend also skips the catalog completion event because
`lastOperation` no longer names that failure. The user sees a stale catalog error
alongside ready/verified state.

**Proposed fix and ownership.** The backend state/IPC owner should model catalog
observation as keyed state rather than as the global last operation: store a bounded
safe receipt projection such as `{request, at, status, failure}` plus a monitor/run
generation, and update it atomically with `codexCatalogVerified`. A later successful
receipt must explicitly supersede the earlier failure by request/generation. The
renderer error owner should derive the catalog notice from that projected state, or
track an error key and clear that same key when the resolving state/event arrives.
Do not use unrelated-operation ordering as the recovery protocol.
