# Update trust and rollback resilience review — code lane 14

Scope: bounded manual read-only review at `e10c52acb23da1c05d401faaa49d0b34c912e830` (`codex/account-limits-login`, tag `v5.6.0-nekodex.3`) of `launcher/electron/update*.cjs`, `launcher/electron/runtime-install.cjs`, and the signed-metadata publication scripts, with only direct supporting reads of `release-trust.cjs`, `resumable-download.cjs`, `atomic-file.cjs`, the readiness call site in `main.cjs`, and `.github/workflows/release.yml`. No tests, builds, exploits, network requests, live authentication, key reads, GitHub actions, source edits, or child agents were used.

## Findings

### 1. [P1] Recovery accepts a pre-existing journal before authenticating its paths, then performs journal-directed filesystem mutations

- **Observed:** `prepareTransaction()` derives a predictable sibling `transactionRoot`, and when that path already exists it immediately reads `transaction.json`; for a stale `preparing` phase it calls `rollback(existing)` and `cleanup(existing)` before creating the updater-owned mode-0700 directory (`launcher/electron/update-worker.cjs:88-104`). This path does not first reject a symlink, verify directory ownership/mode, validate the journal schema/root/job, or constrain operation paths to the expected install target. `rollback()` then trusts each serialized `op.target`, `op.previous`, `op.failed`, and `op.next` for rename and recursive removal (`launcher/electron/update-worker.cjs:194-216`), while `cleanup()` also recursively removes serialized `transaction.job.tempRoot` and can consume serialized recovery registration data (`launcher/electron/update-worker.cjs:312-320`; `launcher/electron/update-recovery.cjs:71-96`). The stricter `schemaVersion` and `root/transaction.json` check exists only in `recover()`, after the normal preparation path has already exposed these sinks (`launcher/electron/update-worker.cjs:355-359`).
- **Failure trigger / inferred impact:** before an update starts, a local process able to create or replace the predictable recovery sibling places a crafted `transaction.json` with `phase: "preparing"`, a non-live worker identity, and attacker-selected absolute operation or cleanup paths. Starting an update makes the trusted launcher execute those rename/removal operations with the launcher's filesystem authority. This is a local confused-deputy path to deletion, replacement, or persistence cleanup outside the update target. The mutation behavior is observed; exploitability is inferred and depends on the attacker being able to write the recovery sibling while lacking direct write access to the victim paths. On layouts where every writer of that sibling already has all launcher permissions, the effect collapses to crash-recovery corruption rather than privilege escalation.
- **Minimal fix and ownership:** the **single update transaction owner** should open/create the recovery directory exclusively and fail closed on any pre-existing object until it is `lstat`-verified as a real directory owned by the current user with private permissions. Before any rollback or cleanup, validate a closed journal schema and recompute every allowed path from the current packaged identity and exact target: require the exact root, target, sibling backup/staging names, runtime and worker paths, and a temp root under the updater's private temp namespace. Reject unknown fields/paths and preserve an unverifiable directory for manual recovery; do not call journal-directed cleanup on it. Apply the same validator in `prepareTransaction()`, `recover()`, and cleanup registration handling.

### 2. [P2] The bundle validated as signed can be replaced through its pathname before the atomic install rename

- **Observed:** the downloaded archive is authenticated against signed metadata and copied into a private temporary directory before extraction (`launcher/electron/update.cjs:543-570`). The worker later copies the staged application to a predictable `.next-<recovery-name>` path beside the installed target and validates that pathname (`launcher/electron/update-worker.cjs:145-160`). After validation returns, the transaction journals/registers recovery and waits for the parent process; `replace()` eventually renames the same pathname into the live target without pinning it to an open directory/file identity or rechecking it (`launcher/electron/update-worker.cjs:161-185`). `validateStagedApplication()` uses `realpath`, `stat`, and subsequent pathname reads, but returns only descriptive paths, not an identity that `replace()` can compare (`launcher/electron/update-validation.cjs:334-404`). Thus signed-metadata authentication proves the bytes originally extracted, while the final rename trusts whatever object occupies `op.next` later.
- **Failure trigger / inferred impact:** after the final validation and before `fs.renameSync(op.next, op.target)`, a local process with write permission on the installation parent renames away `.next-*` and replaces it with another directory or symlink. The worker then installs the replacement without rerunning identity/hash checks. The check/use gap is observed; successful substitution is inferred and requires write access to the target's parent. That permission often already permits direct application replacement, but the gap is still material on shared or helper-mediated installation layouts and breaks the updater's stated guarantee that the installed tree is the authenticated tree.
- **Minimal fix and ownership:** the **same update transaction owner** should keep staged replacements inside the private mode-0700 transaction directory on the target filesystem, validate there, record a stable identity for the staged root and required files, and rename that exact private child into place. Immediately before replacement, verify the transaction root is still the same private non-symlink directory and the staged child's identity matches the validated object; use directory-relative, no-follow/open-handle APIs where the platform supports them. If a platform helper performs the privileged move, pass it a sealed descriptor or independently authenticated digest/identity rather than a mutable public pathname.

## Reviewed controls and limits

The remote trust chain failed closed in the reviewed source: the packaged repository is fixed; release URLs are constrained to the expected GitHub repository/tag/asset path; Ed25519 metadata binds repository, tag, version, validity interval, source fields, asset name, size, and SHA-256; duplicate signer IDs do not count toward threshold; and `checksums.txt` must agree with the authenticated asset hash (`launcher/electron/update.cjs:29-48`, `133-140`, `431-496`, `543-570`; `launcher/electron/release-trust.cjs:36-99`). Publisher code verifies every signed local asset, creates an immutable new draft, compares GitHub's uploaded digest, and only then publishes (`scripts/sign-release-metadata.cjs:8-40`; `scripts/publish-release.cjs:12-37`). The rollback journal is fsynced around state transitions and retains the previous installation until replacement readiness is proven and the commit phase is durable (`launcher/electron/update-worker.cjs:37-44`, `173-217`, `284-343`). No additional concrete important finding was established within the authorized scope.
