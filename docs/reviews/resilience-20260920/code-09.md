# Code review lane 09: cross-platform packaging

Manual bounded review only. Scope inspected: `scripts/build-output.cjs`, `scripts/build-runtime-bundle.ts`, `launcher/scripts/package.cjs`, `launcher/scripts/prepare-runtime.cjs`, `scripts/install.sh`, `scripts/install-launcher.sh`, `scripts/install-launcher.ps1`, `.github/workflows/release.yml`, and the directly called runtime/signing/ABI helpers. No source changes, automated checks, builds, CI, network, live-account work, or child agents were used.

## Findings

### 1. [P1] Standalone installers authenticate a self-reported checksum, but do not bind the artifact to NEKODEX's release identity

- **Observed:** `scripts/install-launcher.sh:124-140` downloads the launcher artifact and `checksums.txt` from the same release and compares their hashes. Its macOS branch only runs generic `codesign --verify` and Gatekeeper assessment at `scripts/install-launcher.sh:153-156`; it does not check the configured Apple team. `scripts/install-launcher.ps1:72-89` follows the same checksum pattern and accepts any `Valid` Authenticode signer without checking the NEKODEX certificate thumbprint or public-key identity. The terminal runtime installer likewise trusts the co-hosted checksum at `scripts/install.sh:39-46`. In contrast, the release workflow creates threshold-signed `release-metadata.json` at `.github/workflows/release.yml:280-283`, and the in-app updater verifies that metadata.
- **Failure trigger / inferred impact:** if a release credential or release-asset set is replaced, an attacker can publish a new artifact and matching `checksums.txt`. A macOS app signed by any accepted Developer ID or a Windows installer signed by any valid Authenticode certificate passes these standalone gates. The checksum still detects accidental corruption; it does not establish the intended publisher/release identity.
- **Proposed fix and ownership:** the **release-trust + installer owner** should make both launcher installers consume and verify `release-metadata.json` against the vendored NEKODEX trust keys, then require the selected asset's exact name, size, and SHA-256 from that authenticated payload. Also pin native publisher identity as a second independent gate: Apple Team ID on macOS and certificate/public-key identity on Windows. Apply the same authenticated metadata path to `scripts/install.sh`, or explicitly retire that path if it is no longer supported.

### 2. [P1] A signal during macOS replacement deletes the only rollback copy before restoration

- **Observed:** `scripts/install-launcher.sh:121-122` registers an `EXIT HUP INT TERM` trap that recursively removes the entire temporary directory. The macOS replacement stores the prior installed app inside that directory at `scripts/install-launcher.sh:166-167`, then copies the new bundle non-atomically into the final application path at `scripts/install-launcher.sh:168-171`.
- **Failure trigger / inferred impact:** if the process receives HUP/INT/TERM, the machine shuts down, or the shell exits while `ditto` is copying, the trap can remove `NEKODEX.previous.app` before the failure branch can restore it. The final path can then contain a partial new app and the previous usable installation is gone. Ordinary `ditto` failure without a signal reaches the explicit restoration branch; the unsafe case is interruption/exit ordering.
- **Proposed fix and ownership:** the **macOS installer lifecycle owner** should stage the complete new `.app` beside the destination on the destination filesystem, keep the previous app in a durable sibling rollback path, and commit with same-filesystem renames. Use one cleanup/rollback handler that restores the previous app whenever commit has started but post-copy validation has not completed; remove the backup only after the installed bundle passes publisher, version/runtime-manifest, and launch-path validation.

### 3. [P1] The Linux ABI gate runs against a rolling-new userspace and cannot enforce an older compatibility baseline

- **Observed:** the release is built on `ubuntu-latest` (`scripts/release-plan.cjs:17`), while `.github/workflows/release.yml:117-123` labels the follow-up as an ABI check but runs it in `archlinux:base` after updating that container to current packages. `launcher/scripts/smoke-linux-appimage-symbols.sh:23-31` checks one bundled libnotify export, and `:34-53` runs `ldd -r` only on the selected top-level executable. It does not cap required GLIBC/GLIBCXX symbol versions, inspect every shipped ELF/native library, or execute under a declared oldest-supported userspace.
- **Failure trigger / inferred impact:** a dependency compiled on `ubuntu-latest` can acquire a GLIBC, GLIBCXX, or other symbol requirement newer than a supported user's distribution. Resolution succeeds on current Arch, so the workflow publishes an AppImage that later fails to load on that older distribution. This is inferred from the direction of ABI compatibility; no artifact was built or executed in this lane.
- **Proposed fix and ownership:** the **Linux packaging/release owner** should declare the oldest supported Linux baseline and build native additions (including libnotify) in that pinned baseline container. Extract the final AppImage and inspect every shipped ELF for symbol-version ceilings, then run the packaged launcher/runtime in the same oldest-supported container. Keep the current symbol-presence check as a narrow regression guard, but do not call it the compatibility gate by itself.

## Review boundary

The owned build-output transaction and macOS packaged-runtime manifest validation appear intentionally staged and rollback-aware in the inspected paths. I did not claim runtime behavior, release viability, or cross-platform compatibility because this lane was restricted to manual source review.
