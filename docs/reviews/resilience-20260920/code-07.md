# Request and continuation lifecycle review — code lane 07

Scope: bounded manual review of `src/responses/{state,parser,schema}.ts`, `src/bridge.ts`, `src/event-queue.ts`, `src/server.ts`, the ChatGPT Web turn/session identity path, and direct launcher account-affinity callers. No source edits outside this report, child agents, automated checks, builds, CI, UI driving, live accounts, network requests, or authentication were used.

## Findings

### 1. High — Local `previous_response_id` replay is not bound to its original task or account owner

**Observed.** `StoredResponseState` retains only timestamps, items, ancestry, counts, and sizes; the global `states` map is keyed only by response ID (`src/responses/state.ts:26-38`). `rememberResponseState()` stores a completed response without an owner identity (`src/responses/state.ts:263-307`). `expandPreviousResponseInput()` accepts any locally known response ID and prepends its entire materialized history without comparing the stored request's task identity to the new request (`src/responses/state.ts:235-249`). The server performs this expansion before parsing and deriving the current turn identity (`src/server.ts:521-535`). Account routing is then derived from the current request's thread/prompt-cache/turn identity (`src/adapters/chatgpt-web/turn-execution.ts:269-290`), not from the owner of the replayed response.

**Failure trigger.** A caller supplies a locally issued response ID from task A as `previous_response_id` in task B. This can happen through a stale/misassociated continuation token or deliberate local API input; random-ID collision is not required. The bridge accepts A's cached messages as B's history and can send them through B's account affinity. That crosses both the task boundary and, in a multi-account launcher, the account boundary. This consequence is inferred from the observed ordering and routing keys; no live account request was made.

**Proposed fix and ownership.** The response-state/continuation owner should store a stable owner descriptor with every node and snapshot entry: at minimum the canonical thread identity used by `chatGptAccountRoutingKey`, plus provider/interaction namespace when those affect where history may be replayed. Change expansion to require the expected owner and fail closed with a distinct owner-mismatch result before materializing any items. The `responseRequest()` owner should extract canonical metadata from the unexpanded body, pass that owner into both remember and expand, and preserve the same check in native passthrough when it expands a Web-owned response. Coordinate the schema migration with the multi-account lifecycle owner; version-1 ownerless snapshot entries should be treated as unavailable rather than adopted by the current task.

### 2. High — A continuation accepted in memory can silently become unrecoverable after a routine restart

**Observed.** Runtime retention allows up to 64 MiB of reachable response history (`src/responses/state.ts:9-10,219-225`), and `rememberResponseState()` reports `retained` after inserting such state (`src/responses/state.ts:290-314`). Disk persistence independently skips every materialized entry larger than 2 MiB (`src/responses/state.ts:11-14,158-169`) and does not persist a non-retained reason. After restart, the missing ID is therefore merely `unavailable` (`src/responses/state.ts:228-232`), and Web continuation returns the generic 409 path (`src/server.ts:562-577`).

**Failure trigger.** A valid response chain grows above 2 MiB but remains below the advertised 64 MiB in-memory cap, which is plausible with image data URLs or a long native transcript. The next turn works while the daemon stays alive. An app update, daemon restart, crash, or machine reboot drops that continuation even though the preceding completion was accepted and reported as retained. The restart-loss result follows directly from the snapshot filter; persistence was not exercised in this lane.

**Proposed fix and ownership.** The response-state persistence owner should make durability an explicit part of retention. Prefer a versioned, bounded node/delta snapshot so a large shared prefix is stored once and descendants do not each require a self-contained payload. If the product intentionally keeps a lower durable cap, return and persist a `not-durable` reason at completion and expose it before a restart can turn a successful continuation into an unexplained 409. The lifecycle owner should flush the bounded snapshot before an authorized daemon replacement and must not describe an entry as restart-retained unless that flush committed it.

### 3. High — Snapshotting performs unbounded synchronous materialization work before applying its disk limits

**Observed.** `persistNow()` runs synchronously on the daemon event loop. For every one of up to 1,000 states, newest first, it materializes the entire ancestry and JSON-serializes that full copy before checking either the 2 MiB entry cap or 24 MiB total cap (`src/responses/state.ts:6,148-176`). Oversized entries take the `continue` branch, so they do not advance the total and cannot trigger the total-cap `break`. The in-memory byte accounting counts shared ancestor nodes once (`src/responses/state.ts:77-89`), while snapshot work repeats those shared bytes for every descendant.

**Failure trigger.** Many retained IDs share a large history, especially a history above 2 MiB. Each debounced persistence pass repeatedly allocates and serializes the same multi-megabyte prefix for every descendant, then discards each oversized result. The 64 MiB reachable-state cap does not bound this repeated work; with 1,000 IDs it can create tens of gigabytes of cumulative serialization work in one synchronous pass, causing request stalls and severe memory pressure. The exact latency and peak memory are inferred from the loop; no benchmark was run.

**Proposed fix and ownership.** The response-state persistence owner should replace self-contained per-ID serialization with one bounded graph/delta pass, or precompute a conservative cumulative byte bound and skip an entry before `materialize()` when it cannot fit. Enforce a per-flush work/byte budget as well as an output-file budget, and move the atomic write preparation off the request event loop if the runtime permits. This should be implemented with finding 2 as one snapshot-format migration so durability and performance use the same limits and accounting.
