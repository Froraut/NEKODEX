## Findings

### 1. `Save proxy` remains actionable when the draft is unchanged, despite a disruptive save contract

**Importance:** High UX/resilience. **Observed rendering:** screenshot `18-account-proxy.png` shows `System settings` already selected with `Save proxy` presented beside it. **Source observation:** `AccountProxySettings.tsx:8-10` keeps a draft and serialized saved value, but `:26` enables the submit button whenever the outer fieldset is enabled; no dirty comparison is used. `AccountSettings.tsx:123-125` disables the form only for general busy state or active turns. `account-pool.cjs:152-170` applies the proxy, closes/recycles connections, saves it, and invalidates account evidence even when the normalized value is unchanged.

**Trigger:** expand Account proxy for an idle account whose saved mode is already `system`, then click `Save proxy` without changing the mode or URL.

**User effect:** a control that looks like an ordinary harmless save can recycle the account browser connection and revoke the checked/connector-ready evidence described directly above it. The user must check the account again despite making no effective change. This is source-proven; the synthetic capture did not execute the mutation.

**Precise fix:** compute a normalized dirty state against `proxy` and disable submit when unchanged. For `system` and `direct`, compare only `{mode}`; for URL modes, compare the validated/normalized mode and URL. Add a short status under the form (`Saved`, `Unsaved changes`, `Saving…`) and keep the backend no-op-safe as a second boundary so an equivalent value cannot recycle connections even if another caller submits it.

### 2. Proxy validation and recovery are detached from the field that needs correction

**Importance:** Medium UX/accessibility. **Observed rendering:** `18-account-proxy.png` shows explanatory prose and controls, but no reserved inline validation/status area. **Source observation:** `AccountProxySettings.tsx:23-25` relies only on `type="url"`, `required`, and `maxLength`; it does not set `aria-invalid`, `aria-describedby`, or a field error. The main-process validator rejects additional cases such as credentials/fragments, a protocol that differs from the selected mode, path/query components, non-HTTPS PAC URLs, and SOCKS5 URLs without a port (`account-network.cjs:6-21`). `AccountSettings.tsx:67-72` sends every rejection to the app-level `ErrorToast` through `setError`; the toast at `App.tsx:3081-3093` is an alert but is not associated with or focused back to the proxy URL input.

**Trigger:** choose HTTP, HTTPS, SOCKS5, or PAC and submit a syntactically valid URL that violates the selected proxy contract, for example an HTTP URL containing credentials or a PAC URL using HTTP.

**User effect:** native HTML validation allows the submit, the server rejects it, and the actionable explanation appears away from the control. A keyboard or screen-reader user is not told programmatically which field is invalid, and focus stays away from the correction point. Exact live toast placement and focus behavior were not exercised; the missing association and validation mismatch are source-observed.

**Precise fix:** share a small renderer-safe proxy validator with the backend rules or mirror the same explicit checks. Give the input a stable error element via `aria-describedby`, set `aria-invalid` only when invalid, show the protocol-specific correction inline, disable submit until valid and dirty, and focus the URL input after a rejected save. Keep backend validation authoritative.

### 3. Account mutations clear `busy` before the returned account state is rendered

**Importance:** Medium control-state/resilience. **Source inference:** `AccountSettings.tsx:67-72` awaits an action but discards its returned `AccountPoolSnapshot`, schedules a later `api.accounts()` refresh, and then clears `busy` in `finally`. The refresh is delayed by 150 ms and can take longer (`:25-47`). Proxy and pacing forms receive only that shared `busy` boolean (`:119-125`). Therefore controls can re-enable against the old rendered proxy/pacing/verification state after a successful mutation and before the follow-up read completes.

**Trigger:** save proxy or pacing on an idle account; the IPC mutation completes, `busy` becomes false, and the scheduled refresh has not returned yet. Slow local I/O or a delayed refresh widens the window.

**User effect:** stale values and stale verified badges can briefly remain interactive, making a duplicate submission possible and hiding that proxy evidence was invalidated. This behavior is inferred from state ordering and was not observed in the static synthetic captures or live Electron.

**Precise fix:** make `run` consume the returned `AccountPoolSnapshot` and call `setState(result)` before clearing the operation-specific pending state. Retain the later refresh only as reconciliation. Track pending state by account/action (`savingProxy`, `savingSafety`, `checkingAccount`, etc.) so the affected control can say `Saving…` or `Checking…` while unrelated accounts remain usable. Announce completion/failure in a nearby `role="status"`/`role="alert"` region.

## Specific polish recommendations

1. **Observed rendering plus subjective preference:** `07-native6-setup.png` has a dense approval paragraph before the connector name and actions. Preserve every account, permission, and Codex approval warning, but break the instructions into three numbered actions and place the exact connector name in a stronger copyable row immediately after the first sentence. This improves scanning without weakening the Native6 approval boundary.

2. **Observed rendering plus subjective preference:** in `05-setup-new.png`, disabled future-step buttons are very low-contrast while the top next-action card duplicates the current sign-in action. Keep the top card as the primary route, but label future disabled actions with a short prerequisite such as `Sign in first` / `Test reply first`, visually or through associated help text. Do not make them clickable early and do not change the isolated DEV/account boundary.
