# UI review lane 01 — Overview and readiness

Baseline: `/Users/alex/Dev/nekodex`, branch `codex/account-limits-login`, source/released baseline `5.6.0-nekodex.3`. This was a manual combined UX/accessibility review of synthetic Electron/React fixture captures and the bounded readiness projection in `launcher/src/Overview.tsx`, `launcher/src/setup-progress.ts`, and `launcher/src/App.tsx`. No source edits, tests, builds, live UI, account access, network activity, or child agents were used. Synthetic fixture state does not prove a real account, connector, runtime, tool execution, or production readiness.

1. `01-overview-ready.png` — synthetic ready Overview, 1360×960 capture / 1360×928 viewport.
2. `02-overview-degraded.png` — synthetic catalog-error Overview, 1360×960 capture / 1360×928 viewport.

## What already works

- The NEKODEX cat identity is consistent without overpowering the primary setup action. The emblem and coding-cat illustration remain recognizably part of one product.
- Connection rows pair status dots with text, so the visible ready/pending distinction does not rely on color alone.
- The ready Overview clearly separates ChatGPT session, models in Codex, and local tools instead of presenting one undifferentiated health light.
- Manual setup explicitly states that connector verification demonstrates availability while a real task demonstrates tool execution. That boundary is correct in the explanatory copy even though the headline described below weakens it.

## Findings

### 1. P1 — A catalog failure is projected as passive waiting after the toast is dismissed

**Observed rendering:** in `02-overview-degraded.png`, the top card says “Model connection installed” and “Waiting for Codex to load the models”; the Models row also says “Waiting for Codex” with a neutral dot. The only explicit failure is the bottom-right toast: “Codex reached NEKODEX, but loading the model catalog failed (HTTP 502; catalog).” The recent event immediately below still reads “Runtime Ready.” Once the toast is dismissed, the durable Overview presents a pending state and no visible failure or direct recovery action.

**Source inference:** `Overview.tsx:17-27` reduces model readiness to `codexCatalogVerified && codexPickerConfirmed`; when core setup is complete but the catalog is false, it always selects `modelsWaitingShort`. The top card uses the same booleans at `Overview.tsx:33-35`. `Overview` receives no current operation/error classification. The error is rendered separately by `App.tsx:408` through the dismissible `ErrorToast` at `App.tsx:3081-3093`, while recent events are an unclassified reverse log slice at `Overview.tsx:65-68`. A known terminal catalog error therefore cannot remain attached to the affected connection row.

**Failure trigger:** catalog verification returns a terminal error, such as the synthetic HTTP 502, after the local runtime has become ready.

**Concrete fix and ownership:** make `App.tsx` own a typed readiness projection for each layer, for example `ready | pending | failed | unverified`, with bounded detail and a recovery destination. Pass that projection to `Overview`. For this state, keep “Local runtime ready” as a separate positive fact, render Models as `Failed to load catalog` with error tone and text, and expose one durable `Retry` or `Open diagnostics` action on the row/top card. Keep the toast as an immediate alert, not the sole persistent record. `Overview.tsx` owns presentation; the `App.tsx` projection owns precedence between operation failure, stored proof, and historical logs.

**Accessibility impact:** the current role=`alert` announces the immediate error, but dismissing it removes the only explicit failure from the visual interface. A persistent textual state and recovery control would support users who miss or dismiss the alert. Keyboard/focus behavior of the toast and proposed retry remains unverified because this lane did not drive live UI.

### 2. P1 — “Models and tools are connected” overstates what the Manual proof establishes

**Observed rendering:** in `15-manual-setup.png`, the highest-emphasis success headline says “Models and tools are connected.” The supporting paragraph then narrows the claim: connector verification confirms availability, while a real task confirms tool execution. Lower on the screen, “MCP configured” is also visible. The headline can be read as end-to-end success even though the screen itself says execution remains unproven.

**Source inference:** `setup-progress.ts:8-14` returns `ready` for Manual mode when tools are installed and `toolsVerified` is true. `App.tsx:60-65` defines current tool proof from persisted MCP completion, connector-name compatibility, and one production runtime-start failure exception; it does not include a successful real tool task. `App.tsx:1573-1581` maps that state to `setupReadyFull` (“Models and tools are connected”) while reusing `setupUseCodex` for the more accurate body. The contradiction is therefore produced by copy/state projection rather than the fixture alone.

**Failure trigger:** Manual setup has a valid local/connector verification receipt but no real Codex task has executed a tool, including a newly created Native6 connector awaiting first use.

**Concrete fix and ownership:** keep the account and native-approval boundary explicit in the primary hierarchy. Rename the terminal setup headline to `Setup checks passed` or `Connector and local tools are available`; show three scoped facts beneath it: `Local runtime ready`, `Connector verified`, and `Real tool task not tested yet`. Change the CTA to `Open workspace and test a tool` when no real-task receipt exists. Do not send a test automatically and do not convert connector visibility into tool-execution proof. `setup-progress.ts` may retain `ready` as workflow completion, while `App.tsx` owns the proof labels and CTA copy.

**Unverified live behavior:** the screenshot is a DEV fixture. It does not establish that Native6 exists in ChatGPT, that a connector was selected for the current account, that approval was granted, or that a tool ran.

### 3. P2 — The configured parallel limit visually reads as measured capacity

**Observed rendering:** both Overview captures give `16` the strongest typographic weight in the metrics strip, followed by “Parallel task limit.” The qualifying sentence, “Active setting; actual simultaneous capacity is not verified,” is much smaller and lower contrast. At a glance, the screen communicates sixteen-way operational capacity more strongly than its own caveat.

**Source inference:** `Overview.tsx:40` renders `snapshot.browserCapacity.active` as the dominant `<strong>` value and places `capacityHint` in `<small>`. The projection is an active setting, not observed simultaneous throughput; the fixture and source do not claim sixteen successful concurrent runs.

**Failure trigger:** any user scans the ready or degraded Overview to decide how much work can safely run in parallel, especially immediately after installation or account changes.

**Concrete fix and ownership:** label the value itself `Configured limit: 16` and add a nearby text badge such as `Capacity not measured`. Keep actual current activity as the separate `Active browser runs` metric. If later runtime evidence exists, show measured capacity as a different field with timestamp/scope rather than replacing the configured-limit label. `Overview.tsx` owns the hierarchy; the settings/runtime owner must remain the source of any future measured value.

**Subjective preference:** a shorter label such as `Limit 16` is visually cleaner, but `Configured limit: 16` is safer because it prevents the dominant number from being mistaken for verified throughput.
