# UI review lane 03 — diagnostics and error provenance

## Audit scope and evidence

Manual combined UX/accessibility review of diagnostics and error provenance in the supplied synthetic Electron/React fixtures. The user goal is to understand what failed, which capability is affected, what remains safe, and the next reversible action without confusing installation, native routing, browser/tool availability, account verification, or approval state.

## Strengths

- The NEKODEX cat identity remains clear without competing with failure information. The Overview uses the mark as a stable product anchor; the update screen keeps the error surface restrained and task-focused.
- The update error explicitly says the previous app remains installed, and the footer says accounts/settings remain in place and the package is verified before installation. This is good safety provenance and preserves user-controlled installation/restart expectations.
- Catalog error copy correctly distinguishes “Codex reached NEKODEX” from a successful catalog load. Source copy also directs persistent failures toward privacy-safe diagnostics rather than exposing account or request payloads (`launcher/electron/main.cjs:338-347`; `launcher/src/i18n.ts:15-16`).

## Findings

### 1. High — Catalog failure is detached from the connection state and produces contradictory guidance

**Observed rendering.** In `02-overview-degraded.png`, the hero says “Model connection installed,” the body says “Waiting for Codex to load the models,” the Models row says “Waiting for Codex,” Recent events says “Runtime Ready,” and a separate generic toast says the catalog failed with HTTP 502. In `06-setup-catalog-error.png`, the primary card says “Models connected · tools not connected” while the catalog-error notification is detached at the bottom edge. A user cannot tell whether the failure means installed-but-temporarily-unavailable, setup incomplete, or a stale notification.

**Source inference.** Overview derives its hero and model row only from saved setup booleans (`launcher/src/Overview.tsx:16-35`, `24-27`). Every non-MCP operation failure is separately copied into one global error string and rendered as `ErrorToast` regardless of the current surface (`launcher/src/App.tsx:255-262`, `400-408`, `3081-3093`). The toast has only a generic “Something went wrong” heading and Dismiss. This architecture explains the detached provenance visible in both fixtures. Whether the exact DEV-profile catalog-error combination can occur with a live account is unverified; the fixture proves the renderer can present it.

**Failure trigger.** A catalog-verification operation emits a 502 after the route/setup booleans already indicate installation or readiness, or the user navigates to another surface while the global failure remains set.

**Concrete fix and ownership.** The parent should assign one setup/connection-state owner to derive a capability-specific display state with explicit precedence: `installed + catalog failed`, `installed + waiting`, `catalog observed + picker unconfirmed`, and `confirmed`. Feed that state into the Overview hero, Models row, and Setup next-step card. Replace the generic catalog toast with an inline status on the affected Models connection and a concise heading such as “Model catalog request failed,” plus “Open routing details” and “View Activity.” Keep the HTTP/stage receipt as expandable diagnostics. Do not imply that native requests, browser tools, account verification, or approvals failed unless their own evidence says so. Use one live-region announcement for the transition so the inline error and toast do not announce the same failure twice.

### 2. Medium — Routing diagnostics explain recovery in prose but do not provide the actions they name

**Observed rendering.** In `06-setup-catalog-error.png`, “Troubleshooting and connection checks” is collapsed while the failure notification tells the user to check routing and Activity. No visible control near the failure opens either destination.

**Source inference.** The Setup next step can open the troubleshooting disclosure and focus its first button (`launcher/src/App.tsx:1566-1589`), and the disclosure contains `RouteDiagnostics` (`launcher/src/App.tsx:1656-1660`). Inside the diagnostic result, catalog failure guidance is rendered as prose after a dense definition list (`launcher/src/RouteDiagnostics.tsx:102-165`). The copy says to check Activity and export privacy-safe diagnostics (`launcher/src/i18n.ts:15-16`), but `RouteDiagnosticsResult` has no action callbacks or controls for either task. The result uses sanitized status/stage/code values, which is a sound privacy boundary (`launcher/src/RouteDiagnostics.tsx:109-123`).

**Failure trigger.** The user follows a catalog-failure toast or opens troubleshooting after a failed receipt. They must infer where Activity is, find an export action elsewhere, and decide whether “Check again” is safe.

**Concrete fix and ownership.** The diagnostics UI owner should render a failure summary above the configuration rows with three explicit, non-mutating actions: “Check again,” “View Activity,” and “Export privacy-safe diagnostics.” Label the evidence as “Latest catalog attempt” with safe timestamp, HTTP status, and stage; label any earlier success separately as historical. Keep route repair/reconnect out of this action group because diagnosis is not authorization to alter Codex routing, account state, or native approval boundaries.

### 3. Medium — Update-check failure offers the right recovery operation under the wrong label

**Observed rendering.** `12-update-error.png` clearly states “Update couldn't finish,” explains that the network was interrupted, and reassures the user that the previous app remains installed. The only primary action is “Check for updates,” which reads like a fresh discovery action rather than recovery from the failure immediately above it.

**Source inference.** `Updates` computes a failure independently of the update state (`launcher/src/Updates.tsx:10-16`). The existing “Try again” copy is used only by the install button when `state.status === "available"`; the check button always uses “Check for updates” unless a check is currently running (`launcher/src/Updates.tsx:32-39`; `launcher/src/update-copy.ts:3-14`). A failed recheck therefore cannot receive the retry label visible in the product vocabulary.

**Failure trigger.** `recheckUpdate()` returns an error or throws after an interrupted network request while the retained update state is idle/up-to-date/error without an available candidate (`launcher/src/App.tsx:629-644`).

**Concrete fix and ownership.** The updates UI owner should retain failure provenance (`check`, `download`, `verify`, or `install`) and label the reversible action accordingly: “Try checking again” for check failures and “Retry download” for a retained available candidate. Never map a generic retry to install/restart; installation must remain a separate user-controlled action. On success, clear the stale failure and announce the recovered state once.

## Specific polish recommendations

1. **Subjective preference:** Keep “Dismiss” visually secondary, but increase its contrast slightly in the toast. In both error fixtures it is easy to miss against the elevated dark surface; the control should remain less prominent than recovery actions while still looking interactive.
2. **Subjective preference:** On the update error card, change the neutral purple download tile to a restrained error treatment or add a small error badge beside the heading. The current icon still reads as an ordinary update state even though the text is a failure.

## Evidence limits and unverified behavior

- No live app, account, route, browser, tunnel, update server, or network behavior was exercised. The synthetic 502 and network interruption do not prove real recovery behavior.
- Keyboard order, focus placement after asynchronous errors, screen-reader announcements, contrast ratios, zoom/reflow, and whether successful recovery clears each visible error remain unverified.
- The diagnostics disclosure was not expanded in an assigned screenshot. Finding 2 combines the visible collapsed state with direct source inspection and is labeled as source inference.
- No claim is made that the synthetic DEV-profile catalog failure is reachable in production. The review is limited to the renderer state shown and the named source branches.
