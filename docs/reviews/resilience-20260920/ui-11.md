## Strengths retained by every recommendation

- The NEKODEX cat identity is recognizable without dominating the operational
  screens. Keep the sidebar mark, ready-state emblem, and coding-cat art.
- The pages use stable headings, restrained color, and consistent cards. The
  titlebar breadcrumb and selected sidebar item provide useful location cues.
- Accounts, model/catalog readiness, and local-tool readiness are shown as
  separate facts. Preserve those boundaries: an authenticated account is not a
  verified model route, and neither is a verified Native connector.
- The Native6 step explicitly says command/edit actions remain subject to ChatGPT
  permissions and Codex sandbox/approvals. IA simplification must not collapse or
  weaken that approval explanation.

## 1. P1 — One connection journey is split across three destinations and four names

**Screenshot evidence:** `01-overview-ready.png`, `13-settings.png`, and
`07-native6-setup.png`.

**Observed rendering:** the sidebar presents `Setup` and `Codex tools (MCP)` as
separate peers under `Configuration`. Overview calls the same readiness areas
`Models in Codex` and `Local tools`, each with a `Manage` action. Settings contains
another Native6 configure/upgrade/verify entry. The MCP screen then presents a
three-step connection flow whose final step is titled `Attach the ChatGPT
connector`. Each individual label is understandable, but they do not establish
one obvious answer to “where do I connect or repair NEKODEX?”

**Source observation:** `App.tsx:890-927` creates three sidebar groups, including
separate `setup` and `mcp` surfaces; `App.tsx:957-1004` mounts those as independent
pages. Settings can redirect to MCP and also owns the Native6 action
(`App.tsx:1012-1018, 2352-2372`). Overview maps account/model/tool readiness to
three more labels and destinations (`Overview.tsx:24-28, 59-63`).

**Failure trigger / source inference:** an existing user who needs to upgrade to
Native6, repair a model catalog, or restore local tools can reasonably choose
Overview `Manage`, sidebar `Setup`, sidebar `Codex tools (MCP)`, or Settings. The
result may still be correct, but the user has to understand internal boundaries
before choosing a starting point. This is an IA inference from the rendered and
source routes; navigation behavior was not driven live.

**Concrete fix and ownership:** give connection work one top-level entry called
`Connections`. Its landing surface should show two independent, status-bearing
sections: `Models and Codex route` and `Local tools connector`. Each section keeps
its current proof, repair action, and separate completion criteria. Existing
`SetupSurface` and `McpSurface` can remain as internal subroutes, so this does not
require rewriting either workflow. Move the Settings Native6 mutation into the
local-tools section; Settings should contain a `Manage tools connection` link only.
Use the same names in Overview connection rows and the Connections landing page.

**Acceptance:** from Overview or the sidebar, a user has one connection entry;
the landing page visibly distinguishes account session, model-route readiness,
and local-tool connector readiness; Native6 upgrade/verification is found there;
and tool permissions plus Codex approval boundaries remain explicit before the
external ChatGPT step.

## 2. P1 — Account cards mix four different concepts without a state-driven next action

**Screenshot evidence:** `03-accounts.png`.

**Observed rendering:** each card combines identity, selected-browser state,
active-task count, model check, local-tools check, a `Use for new tasks` checkbox,
credential sign-in/replacement, selection, two verification actions, pacing, and
proxy settings. The first card shows `Selected` in both its header and action row.
The second card is enabled for new tasks while `Local tools: Needs setup`, and its
four adjacent actions have similar visual weight. The user must infer whether the
next task is sign-in, selection, account check, connector check, or setup elsewhere.

**Source observation:** the account page renders routing globally and then places
all facts and controls in each card (`AccountSettings.tsx:77-128`). Selection,
eligibility, authentication, model evidence, and connector evidence are distinct
state fields, but the UI presents them as one facts row and one actions row
(`AccountSettings.tsx:87-117`). Pacing and proxy are correctly secondary details
but appear immediately after that crowded action row (`:119-125`).

**Failure trigger / source inference:** add a second account that is signed in but
has incomplete capability or connector evidence, as shown by the fixture. A user
can see `Use for new tasks` before understanding whether the account is eligible
for the requested model/tools, while `Selected` describes the browser surface and
does not necessarily describe balanced routing. Continuing tasks must remain bound
to their original account, so simplifying this screen must not imply that changing
selection migrates a running or retained task.

**Concrete fix and ownership:** restructure each card into three explicit layers:

1. `Account` — label/login identity plus `Current browser account` when selected.
2. `Readiness for new tasks` — Session, Models, and Local tools as a checklist,
   each with a contextual action only when evidence is missing or stale.
3. `Routing and advanced controls` — `Eligible for new tasks`, followed by collapsed
   pacing/proxy settings. Explain once that existing tasks remain on their original
   account.

Show one primary next action derived from state: `Sign in`, `Check models`, `Check
connector`, or `Ready`. Keep `Replace credentials` as a secondary recovery action,
not the primary action on an already verified card. Preserve separate checks and
do not infer connector readiness from account authentication.

**Acceptance:** each card has one unambiguous next action; `Current browser
account` and `Eligible for new tasks` cannot be mistaken for each other; incomplete
model/tool readiness remains visible before new-task eligibility; and retained or
running task ownership is stated without offering migration.

## 3. P2 — Settings section labels do not describe the controls they contain

**Screenshot evidence:** `13-settings.png`, with `07-native6-setup.png` as the
destination duplicated by one Settings control.

**Observed rendering:** `DEV profile settings` opens with a large two-card
Automatic/Manual choice, then `Parallel agents` and two model selectors. Lower on
the same long page, `Workspace preferences` begins, but source shows that section
also contains browser/login behavior, manual timing, Native6 connection management,
context/model features, language, and diagnostics. This creates a clean visual
column with a weak conceptual scan path.

**Source observation:** the first heading is `Agents and models`, followed by mode,
capacity, compaction model, and Pro model (`App.tsx:2267-2320`). The next heading is
implemented with the copy key `appearanceLabel` / visible text `Workspace
preferences`, but underneath it are keep-running behavior, passkey browser, manual
submit timeout, browser visibility, Native6, advanced context/tool behavior, and
language (`App.tsx:2321-2431`). Diagnostics follows separately (`:2440-2470`).
`tokens.css:57-68` supplies a readable type/width scale; the problem is grouping,
not a missing global visual system.

**Subjective preference, explicitly separated:** I would prefer four short sections
over one long settings stream because the controls already describe four user
intentions. This preference is based on scanability in the supplied 1360×960
fixture; no user study or live scroll timing was performed.

**Concrete fix and ownership:** regroup without changing control behavior:

- `Execution` — Automatic/Manual mode, parallel task limit, show-browser behavior,
  and manual submission timeout.
- `Models and context` — Pro/summary model choices, Bigger Context, skill
  attachments, Web subagents, fresh conversation, and context-budget evidence.
- `Application` — launch/keep-running behavior, passkey browser, and language.
- `Diagnostics` — current diagnostic and recovery rows.

Remove Native6 configuration from Settings under finding 1. Replace the misleading
`appearanceLabel` key/name; this surface currently has no appearance controls.
Keep advanced model/context toggles collapsed by default, but automatically expose
the pending or failed item as the existing source already does.

**Acceptance:** every setting has one predictable section; changing interaction
mode and task capacity remains easy to find; model/context controls are together;
application behavior is separate; connection setup has no duplicate mutation path;
and the page can be scanned from section headings without reading every description.

## Two specific polish recommendations

1. **Keep the Overview cat card, remove its duplicate navigation buttons.** In
   `01-overview-ready.png`, `Open workspace`, two clickable metrics, three
   connection `Manage` rows, and the cat card's `Manage accounts` / `Open browser`
   repeat the same destinations. Keep the cat illustration and copy as NEKODEX
   identity, keep the hero as the single primary action, and keep Connections as
   the canonical repair area. Make the art card informational or retain at most one
   context-dependent shortcut (`Overview.tsx:32-42, 59-78`). This is a subjective
   hierarchy preference, not evidence that the current buttons malfunction.

2. **Make the exact connector name impossible to miss and easy to copy.** In
   `07-native6-setup.png`, the `Connector name` row is visible but the value is not
   legible in the supplied rendering, even though source renders it in a code pill
   (`App.tsx:1969-1972`; `styles.css:1771-1789`). Put the exact value directly below
   the instruction in a full-width read-only field with a `Copy name` button and a
   brief copied confirmation. Treat the fixture's unreadable value as an observed
   synthetic-rendering issue; live text population and clipboard behavior remain
   unverified.
