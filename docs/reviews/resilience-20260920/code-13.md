# Account credentials and quota resilience review — code lane 13

Scope: bounded manual review of the new `launcher/electron/account-quotas.cjs` and `launcher/electron/codex-login.cjs`, plus the direct account/session ownership contracts in `account-pool.cjs`, `account-registry.cjs`, `account-network.cjs`, `browser-host.cjs`, `profile.cjs`, and `main.cjs`. No source edits, tests, builds, exploits, network requests, live authentication, credential reads, or child agents were used.

## Findings

### 1. [P1] Device-login completion can replace the shared Codex credentials after cancellation or account selection changes

- **Observed:** `createCodexLoginController()` launches the official account service with the real shared `CODEX_HOME` (`launcher/electron/codex-login.cjs:363-369`), and its public snapshot explicitly describes that target as `shared-codex-auth-store` and reports `cliAuthSaved` on completion (`launcher/electron/codex-login.cjs:185-207`). `handleMessage()` accepts a matching successful `account/login/completed` notification and sets `completed` without requiring the flow still to be `waiting` or the selected account still to equal `current.accountId` (`launcher/electron/codex-login.cjs:265-304`). In particular, the success branch precedes the `cancelling` branch. The selected account is checked before the device code is exposed (`launcher/electron/codex-login.cjs:404-416`), but it is not checked at completion. `cancel()` changes the phase to `cancelling` and then awaits the cancel RPC, leaving a window in which the success handler can change the same flow to `completed` (`launcher/electron/codex-login.cjs:441-456`).
- **Failure trigger / inferred impact:** (a) the user cancels while authorization completes, or (b) starts login for account A, switches the launcher selection to B after the code is shown, and then completes the device flow. A success notification in either window is treated as authoritative completion. Because the child is operating directly on the shared auth store, the official service may already have persisted the new CLI credentials before NEKODEX receives that notification; NEKODEX can therefore report a cancelled or differently selected flow while the shared Codex identity has changed, or can report completion bound to stale local account A while B is selected. Persistence-before-notification is inferred from the controller's shared-home contract and `cliAuthSaved` state; no live auth store was read.
- **Minimal fix and ownership:** the **single account/auth lifecycle owner** should run each device flow against a private per-flow staging `CODEX_HOME`. On successful notification, promote only the expected auth artifact into the shared store after atomically checking `flow === current`, `current.phase === "waiting"`, and `selectedAccountId() === current.accountId`; cancellation, timeout, selection change, or destruction must discard staging. Also serialize account selection with an active device flow, or cancel and fully terminate the staged flow before committing the new selection. Merely reordering the notification branches would fix the displayed phase but would not undo credentials already written to the shared home.

### 2. [P2] A cleared or superseded quota epoch can still resolve stale account data to its original caller

- **Observed:** `AccountQuotaReader.clear()` only deletes the map entry (`launcher/electron/account-quotas.cjs:277-280`). `read()` captures a mutable `state`, starts `#readLive()`, and returns that promise's result directly; its completion handler updates and returns the captured state without checking that `this.accounts.get(accountId) === state`, that the same Electron session still owns it, or that the evidence epoch is still current (`launcher/electron/account-quotas.cjs:293-335`). Session and epoch equality are checked only before the request starts and when a later snapshot/read considers reusing the cache (`launcher/electron/account-quotas.cjs:282-304`).
- **Failure trigger / inferred impact:** a quota read begins for an authenticated per-account session, then logout, reauthentication, proxy/session replacement, or another evidence invalidation clears or supersedes that account while the two remote requests are in flight. Future reads will not reuse the old state, but the original awaited call can still resolve successfully and its consumer can publish quota/plan data obtained under the prior auth session as current data for the local account. This is an inferred stale-disclosure and account-misbinding effect; the module has no integrated caller in the inspected tree yet, so whether a higher layer independently rejects the result remains unresolved.
- **Minimal fix and ownership:** the **quota/account-session lifecycle owner** should give each read an owned cache-generation token and, before resolving a successful or unavailable result, require that the map still points to that exact state and that its session and epoch match. `clear()` and owner/epoch replacement should abort the old request where practical. Return a distinct stale/cancelled result (or reject) so callers cannot render it, and require the integrating caller to compare the account's current evidence epoch again immediately before publication.

## Reviewed controls and limits

The quota reader uses manual redirects and exact final-URL checks before reading the session token or forwarding the bearer token (`launcher/electron/account-quotas.cjs:149-152`, `343-375`), bounds response/token sizes, and checks an optional usage `account_id` against the token claim (`launcher/electron/account-quotas.cjs:114-131`, `159-234`). `AccountBrowserPool` creates a distinct persistent Electron partition per local account and applies that account's network policy to its session (`launcher/electron/account-pool.cjs:64-79`). These controls did not yield an additional concrete finding in this bounded review. The two new modules are currently untracked and not yet wired to callers in the inspected checkout, so integration behavior is reported only where direct contracts establish it; no runtime or credential-state claims were made.
