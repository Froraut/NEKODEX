# UI review lane 08: Statistics and data clarity

## Scope and evidence

Manual UI/source review only. The captures are explicitly synthetic React/Electron fixtures and do not verify a live account, real usage totals, network behavior, approval state, or installed-runtime behavior. No source files, tests, builds, live UI, accounts, network state, or child agents were used.

Images viewed with `view_image`:

1. `08-usage-web.png` — Web, populated seven-day report.
2. `09-usage-native.png` — Native, populated seven-day report and token coverage.
3. `10-usage-empty.png` — Web, synthetic zero-total report.

Sources inspected:

- `launcher/src/UsageDashboard.tsx`

## Findings

### 1. P1 — Display labels are used as data identity, causing duplicate React keys and lossy exports

**Screenshot evidence:** `08-usage-web.png` shows the all-accounts Web scope and the collapsed detailed breakdown. The capture run emitted real React duplicate-key warnings for `automatic · high · GPT-5.6` when three synthetic accounts shared that classification.

**Observed rendering/runtime evidence:** The warning proves that at least three rendered lifetime rows were assigned the same key. Duplicate keys make React row reconciliation undefined: a later refresh, filter switch, or expansion can reuse, omit, or update the wrong row even when the visible first frame appears normal.

**Source evidence:** `UsageDashboard.tsx:19–23` creates `groupLabel` without `accountId`. `UsageDashboard.tsx:25–34` uses the resulting display name as `<tr key={name}>`. Period rows are intentionally merged through a `Map` at `UsageDashboard.tsx:189–199`, but lifetime rows bypass that merge and are mapped directly to label/row tuples at `UsageDashboard.tsx:309–312`; three accounts with the same mode, effort, and model therefore produce three identical keys. Export loses still more identity: `exportReport` groups Web rows only by `modelVersion` at `UsageDashboard.tsx:68–82`, dropping account, mode, effort, model-version source, and message kind even though the button says “Export displayed CSV.”

**Failure trigger:** Expand “Detailed breakdown” with “All accounts” selected when two or more lifetime groups have the same mode/effort/version label, as in the three-account synthetic fixture. Export any Web report containing multiple modes, efforts, accounts, or message kinds for the same model version.

**Source-based inference:** The table can render unstable lifetime rows, while the CSV can merge materially different displayed classifications into one model row. The screenshots do not prove that a user has already received an incorrect live export.

**Precise fix suggestion:** Introduce a canonical group identity that includes every semantic dimension (`accountId`, mode, effort, model version/source, message kind; native endpoint/model source/model ID where applicable) and keep the localized display label separate. Decide explicitly whether all-account tables aggregate across accounts: if they do, aggregate rows before rendering and use the canonical aggregate key; if they do not, include the account label in the row label. Use the same normalized grouping contract for the table and CSV, adding explicit columns rather than flattening to model version. Ownership should stay with one Statistics data-presentation owner because table reconciliation and export semantics must match.

### 2. P1 — The zero-total state can display nonzero historical-looking durations as if they belong to the empty period

**Screenshot evidence:** `10-usage-empty.png` shows all five Web outcome cards at `0`, “Not available” for the known-outcome completion rate, and “0 accepted messages across 0 of 7 days.” Beside those zero-period values it still shows median `2.2 sec`, 95th percentile `3.2 sec`, and “Accept-to-outcome duration for 5 observed messages.”

**Observed rendering:** The same period simultaneously claims zero accepted messages and five observed duration samples. The duration card has no stale, lifetime, or previous-period label, so the visible report is internally contradictory.

**Source evidence:** `UsageDashboard.tsx:274–281` renders `visible.durations` independently of `visible.metrics.total` and `knownOutcomeTotal`. The only zero-period treatment is an additional paragraph after the chart at `UsageDashboard.tsx:308`; existing metric, duration, calendar, failure, and export UI remains active. The renderer performs no consistency check such as `observedSamples <= metrics.total`.

**Failure trigger:** Any snapshot/fixture/cache or future migration returns `metrics.total === 0` while retaining duration samples. The assigned synthetic empty fixture demonstrably reaches this state. Current live `UsageStore` behavior was not exercised, so whether its present API can emit this contradiction is unverified.

**Source-based inference:** Users can read stale or mismatched durations as measurements for the selected empty period and export the same contradiction in the summary row. This is a resilience boundary problem even if the current backend normally emits coherent snapshots.

**Precise fix suggestion:** Validate report coherence at the renderer boundary before display/export. For a zero-total period, require zero observed duration samples and null quantiles; otherwise show a compact “Report data is inconsistent—refresh” notice and suppress duration values and export. For the normal empty state, replace the full chart/insight stack with a concise empty-period panel while retaining filters and the date range. Keep lifetime data available only inside the explicitly labeled lifetime disclosure.

### 3. P2 — Native mode visually and semantically says “All accounts” even though account attribution is unavailable

**Screenshot evidence:** `09-usage-native.png` shows a disabled Account control whose value is “All accounts,” immediately beside explanatory copy saying native token accounts are not linked to browser accounts.

**Observed rendering:** “All accounts” conventionally means an aggregation across known accounts. Here it is displayed for data that has no browser-account dimension. The explanatory note corrects the meaning, but only after the misleading value has already framed the report.

**Source evidence:** `UsageDashboard.tsx:242–247` keeps the Web account `<select>` visible in Native mode, forces its value to the empty option, and disables it; the empty option is always `usageAllAccounts`. `exportReport` sets every Native export to `scope = "all"` at `UsageDashboard.tsx:66–68`, preserving the same ambiguous meaning in CSV. The code correctly prevents an account ID from being sent for Native queries at `UsageDashboard.tsx:158–160`; the defect is presentation and export terminology, not an account-authorization bypass.

**Failure trigger:** Select Source = Native or export a Native report.

**Source-based inference:** A user can reasonably interpret the report/export as complete across all configured ChatGPT accounts, even though the data is only unattributed activity observed through NEKODEX’s native proxy. The synthetic capture does not prove any real account association or full native-activity coverage.

**Precise fix suggestion:** In Native mode remove the account selector from the form layout or replace it with a noninteractive “Account attribution: Not available” field. Keep the existing explanation that native token identities are not browser accounts. Export Native rows with an explicit scope such as `native-unattributed` and an empty account field; do not call the scope `all`. This change belongs to the Statistics UI/export owner and must preserve the current account and approval boundary.

## Specific polish recommendations

1. **Subjective preference:** In `09-usage-native.png`, the six equal-width metric cards make “Native proxied requests” and “Outcome unrecorded” wrap heavily while short labels leave unused space. Let the total card span two columns or use a responsive 3-by-2 arrangement for Native; retain the current color restraint and card style.
2. **Subjective preference:** Token coverage copy such as “1 reported samples” is visually repetitive and grammatically awkward. Present each value as `100 · 1/1 reports` (and `— · 0/1 reports`) or use plural-aware localized copy, while keeping missing usage visibly unknown rather than converting it to zero.

## Evidence limits

The screenshots establish the rendered synthetic states and the duplicate-key warning supplied by the capture run. Source inspection establishes the key construction, grouping, export, and conditional-rendering paths. Keyboard operation, focus retention after filter changes, screen-reader announcements, CSV file contents in a real Electron session, narrow responsive behavior, live account data, native-token identity, approval state, and installed `5.6.0-nekodex.3` runtime behavior remain unverified in this lane.
