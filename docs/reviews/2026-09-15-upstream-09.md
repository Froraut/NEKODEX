## Deduplication and boundaries

- #457's image-support follow-up and #458 express one product request. #488 is a separate validation defect: the adopted guard improves where unsupported Web *requests* fail and does not enable Manual screenshots, resolve Codex modality stripping, or repair Windows native bindings.
- Already addressed: automatic inline-image attachment preparation; explicit `file_id`-only tool-image refusal from the coding iterations. Still unproved: live Computer Use image delivery on the reporter's platform/account and all browser image acceptance conditions. The coding-iteration report's focused checks concern the stated source contracts, not these live flows.
- Tally: **1 narrow source defect adopted but unverified (#488), 1 optional image-handoff feature (#458, deduplicating #457 follow-up), 1 mixed external/insufficient-evidence incident (#457).** No blanket upstream patch adoption recommended.

## Local implementation handoff

- Changed `src/server.ts`, `src/adapters/chatgpt-web/browser-worker.ts`, and new `src/adapters/chatgpt-web/input-image-validation.ts`; no tunnel or service files were changed in this lane.
- Added **one named focused test** in `tests/server-web-image-validation.test.ts` for remote URL and BMP rejection before adapter creation and successful passage of a valid inline PNG to automatic and Manual adapters. It was **not executed** under the parent's shared verification budget. HTTP 200 in its stub path would only mean the adapter was reached, not that ChatGPT accepted an image.
- Only URL form and allowed MIME type are validated early. The existing worker still enforces base64 integrity, nonempty bytes, per-image/count/total size limits. File-ID-only user references remain text references; file-ID-only tool-result images remain explicitly rejected by the coding-iteration change. Manual still advertises text-only capability and requires a human image attachment.
