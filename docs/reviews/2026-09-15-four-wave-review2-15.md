## Repeated candidate, not a new R2 finding: R1-15-1

**Trigger and consequence.** After a v11 JSON installation is disconnected and both inactive journal copies are identical, a different actor restores the exact command entry at the journal's recorded Interrupt group/hook index. `route status` (`src/cli.ts:334-343`) calls `inspectCodexIntegration()` (`src/codex-integration.ts:748`), whose `readJournal()` reconciles the inactive hook (`src/codex-integration-journal.ts:329-331,256-268`). `restoredInactiveJsonHook()` verifies the entry's index and canonical hash, then produces its removal (`src/codex-integration-journal.ts:225-238`; `src/codex-interrupt-hook-json.ts:120-140,191-208`). The guarded writer checks the full current bytes before the write (`src/codex-integration-shared.ts:371-381`), but cannot identify who inserted an identical entry. The status read can consequently delete the later actor's hook and report the now reconciled state. This is the same ownership ambiguity as **R1-15-1**, not a second defect.

**Additional direct callers of the same root.** `subagents status` and `doctor` call inspection (`src/cli.ts:360-365`; `src/doctor.ts:151`); `readCodexSubagentProtocol()` calls `readJournal()` (`src/codex-integration.ts:223-229`), including from `GET /v1/models` (`src/server.ts:1092-1112`) and setup preparation (`src/setup.ts:467-476`). Thus a catalog read can also reconcile that inactive hook; the first-wave description as a *status* read was an example, not the whole surface. Do not assign a new R2 ID for these routes.

**Counterevidence and limit.** A different entry hash, occupied foreign slot, or duplicate command elsewhere fails closed (`src/codex-integration-journal.ts:239-253`; `src/codex-interrupt-hook-json.ts:135-158`); a concurrent byte change before removal aborts the guarded write (`src/codex-integration-shared.ts:372-378`). Repeated direct disconnect explicitly opts out of reconciliation and refuses an occupied inactive hook (`src/codex-integration.ts:511-534`). The intended recovery also needs to complete an interrupted disconnect after journal/config writes but before hook removal (`src/codex-integration-shared.ts:423-430`). The provenance ambiguity requires the later actor to restore the **exact** entry in the **exact** slot, with a matching restored config; it is a conditional source finding, not a demonstrated live failure. The upstream report's repeated-disconnect correction covers the direct disconnect path (`docs/reviews/2026-09-15-tunnel-upstream-results.md:35`), so it does not refute this indirect read path. No first-wave claim is rejected on the inspected evidence.
