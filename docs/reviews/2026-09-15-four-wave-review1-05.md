## Potential findings

- **R1-5-1 — Existing DEV tunnel is not re-established after a failed setup commit.** Trigger: a Full DEV profile already has a running supervised tunnel; generation-4 active-name migration or a version/credential change requires bootstrap (`src/setup.ts:966-971`), `connectTunnel` succeeds, validation `stopTunnel` succeeds (`src/setup.ts:442-455`), and then the config concurrency guard or `saveConfig` fails (`src/setup.ts:975-980`). Rollback restores the owned profile/key/client/config (`src/setup.ts:989-1027`) but never reconnects the previously running `existing` tunnel. Consequence: a failed transaction can leave the former DEV MCP runtime stopped; subsequent named chat rejects the unready tunnel (`src/dev-chat/transport.ts:35-40`). Counterevidence/qualification: the launcher owns ongoing supervision (`src/dev-chat/transport.ts:25-27`) and may reconnect autonomously; that recovery is not demonstrated by this setup path. The ordinary successful commit intentionally stops validation for the launcher to reconnect. Scope the fix to prior-running-state recovery on failed setup, without renaming Native4 DEV/Zero Risk4 or changing the public contract.

- **R1-5-2 — Chat cleanup can mask its initiating error.** Trigger: `driver.send`/interactive chat throws and either `driver.close()` or `transport.close()` also rejects. The `finally` block at `src/dev-chat/cli.ts:429-437` throws an `AggregateError` containing only cleanup rejections. Consequence: the original chat failure disappears from the CLI exception chain, hindering direct failure diagnosis. Counterevidence: `Promise.allSettled` does close both resources and reports both cleanup failures when the chat itself succeeds; no defect in that success path. Preserve the primary exception in the combined failure when both fail.
