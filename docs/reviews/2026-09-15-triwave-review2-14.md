## New concrete finding

### T2-14-1 — An exceptional production status probe aborts the CLI diagnostic report

**Trigger:** A valid Full configuration is present, but a status subprocess cannot complete. One concrete path is `launchctl print` timing out during `getTunnelServiceStatus()`; another is the managed `tunnel-client runtimes status ... --json` timing out. `runCommand()` in `src/process.ts:24-35` throws `spawnSync`'s `result.error`, including `ETIMEDOUT`, instead of returning a `CommandResult`.

**Exact source and direct callers:** `getTunnelServiceStatus()` calls `runCommand("launchctl", ...)` with a 5-second timeout at `src/tunnel-service.ts:88-104`; `tunnelStatus()` calls `runCommand()` with a 10-second timeout at `src/tunnel.ts:556-566`. Production `runDoctor()` calls these helpers without per-check catches at `src/doctor.ts:193` and `:208`; its report is constructed only after all checks at `:222-226`. The `doctor` and top-level `status` commands share `doctorCommand()` at `src/cli.ts:318-324,527`, so `runDoctor()` rejection reaches the top-level error handler at `src/cli.ts:570-572` and neither JSON nor human-readable report is printed. The `tunnel status` command likewise obtains runtime and service before printing at `src/cli.ts:448-452`; either thrown probe prevents its `{ service, runtime }` JSON from being emitted.

**Consequence:** On precisely the status failure an operator needs to diagnose, `doctor --json`, top-level `status`, or `tunnel status` can produce only a stderr error and exit 1. For `doctor`, the already assembled config, browser, Codex route, service, and proxy checks are lost. For `tunnel status`, the independent status that succeeded is lost. This is a diagnostic/reporting defect, not evidence that the tunnel runtime or connector itself is down.

**Counterevidence and boundary:** Ordinary nonzero or non-JSON tunnel-client output does not take this path: `parseTunnelStatus()` at `src/tunnel.ts:521-553` turns it into `{ ok: false, detail: ... }`, so the CLI can print its report. An ordinary nonzero `launchctl print` is likewise represented as unloaded at `src/tunnel-service.ts:97-104`. The defect requires an exceptional subprocess result (such as timeout or spawn failure), not merely an unhealthy runtime. `src/setup.ts` has explicit unknown-ownership handling for some status probes, but that rollback logic does not guard these read-only CLI callers. No runtime failure frequency or live connector attachment was established.

**Disposition:** New production CLI status root. A minimal correction would represent each probe exception as a failed diagnostic check or status field while preserving the independently obtained checks and a failing exit code. No Native4 / Native4 DEV / Zero Risk4 App ID, name, tool, or schema change is needed.
