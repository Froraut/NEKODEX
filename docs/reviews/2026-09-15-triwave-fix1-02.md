# Triwave fix 1, lane 2 — direct service install

Baseline: `3740505b0107af9a83053fd523ae1ad30be36465` (`HEAD`). Implementation wave 1 of 3, lane 2. Source ownership was limited to `src/service.ts`; this handoff report is the requested coordination artifact.

## Fixed finding

**T2-2-1 / P2 — fixed in `src/service.ts`.**

`installService(config)` now obtains the current service status and renders the next plist definition before any filesystem mutation. If the service label is loaded and the existing definition is missing or differs from the rendered definition, it throws:

`Refusing to replace a loaded service definition; stop it before installing the update`

The rejection occurs before `mkdirSync`, `atomicWriteFile`, the definition-written callback, or bootstrap. This prevents a direct `service install` from publishing a new disk definition while leaving the old loaded daemon active. The caller still receives the existing thrown-error behavior and the public `ServiceStatus` shape is unchanged.

An already loaded service with the same definition remains a successful no-op. An unloaded service retains the prior behavior: write the changed definition, invoke the optional ownership callback with the exact bytes, bootstrap the service, and return a fresh status.

## Cross-lane handoff

The direct CLI path in `src/cli.ts` can continue calling `installService(config)` unchanged. The explicit restart/drain path remains owned by setup and `restartService(config)`; this fix deliberately does not add an implicit drain or restart to direct install.
