## Решение о последовательности

Рекомендуемая очередь: **D01/P02 (текущий этап) → DW1–DW2 → DW5 → DW6–DW7 → DW9**. Сначала реализация защищённых tunnel credentials по уже установленному D01/P01 source-контракту, затем клиентская панель плана/результатов и reusable workers, затем разрешаемая пользователем история с поиском/ветками и ручной Goal helper. Это последовательные небольшие результаты, а не один большой релиз. Внутри неё не требуется второй исполнитель задач Codex. Из оставшегося самое полезное последующее расширение — ручные code snapshots с выборочным restore (DW8), затем ограниченный автоматический Goal (DW10) при готовой durable delivery boundary.

Параллельно остаётся довести N01–N08 через содержательное ревью. SSH, IDE, собственные workers и универсальное управление компьютером не становятся обязательными только потому, что есть у CoS. NEKODEX сейчас обслуживает клиент, который уже владеет рабочей папкой, Git, инструментами и исполнением. Новый второй владелец требует самостоятельного продуктового основания. При этом клиентская интеграция существующего плана, состояния workers, fork и истории — самостоятельная полезная функция; она не отвергается как «дублирование» только из-за наличия соответствующей capability у клиента.

- **Следующим** — конкретный следующий ограниченный результат. Зависимость в строке задаёт порядок работ, а не дополнительный вопрос о разрешении.
- **Позже** — полезная возможность с указанным условием начала; сейчас её не реализуем.
- **Отклонить** — не переносить в текущий продукт. Пересмотр возможен при изменении его роли, а не после произвольного ожидания.
- **P1 / P2 / P3** — обязательность для выбранного результата / полезное расширение / отдельное расширение продукта. Оценка относится к внедрению идеи, а не к срочности обнаруженной ошибки.

Для DW1/DW9/DW10 `verified` требует реально наблюдённого исхода в его точной границе: source call/event ID, subject revision/hash, вид проверяемого свойства и outcome. Модельные `completed` или `check_evidence=true` этого не заменяют. Связь evidence → требование остаётся семантическим выводом helper и показывается со ссылкой; успешный tool call не сертифицирует бизнес-результат. Без исходного события/актуального артефакта — claimed/unknown. Helper получает выбранные bounded/redacted подтверждения, не весь raw tool transcript автоматически.
