## New conditional finding

**R2-5-1 — Full-to-browser-only DEV CLI setup leaves a formerly owned MCP tunnel running.** Trigger: an isolated Full DEV profile has an active launcher-supervised MCP tunnel, then its owner runs `dev setup --browser-only` from the CLI (`src/dev-chat/cli.ts:345-377`). `configureTunnel` deletes all tunnel fields (`src/setup.ts:357-361`), and `setupDevProfile` skips both bootstrap and `stopTunnel` for browser-only before committing the new config (`src/setup.ts:962-980`). Consequence: the old tunnel can continue running under the former alias despite the newly saved browser-only profile; `RuntimeSupervisor.startConfigured` explicitly labels a still-owned DEV MCP runtime in this mode `external` rather than adopting or stopping it (`launcher/electron/runtime-supervisor.cjs:1282-1292`). Later `dev chat` uses browser-only and does not attach a Full transport (`src/dev-chat/cli.ts:408-410`), so the process is stranded from that CLI's normal path. Counterevidence/limits: the launcher may already have stopped the tunnel as part of a separate setup workflow or may be closed; this requires the specified live-owner trigger. The supervisor's external-state check is a deliberate safety guard, not a claim of silent readiness. A direct CLI invocation has no `stopForSetup` handshake, and stopping blindly while turns are active would violate the ownership boundary (`launcher/electron/runtime-supervisor.cjs:2141-2215`). Resolve within the existing DEV owner/idle-drain contract; preserve Native4 DEV and Zero Risk4 identity and public schema.

## First-wave challenge and duplicates

- **R1-5-1 repeated, conditional, not a new R2 ID.** A successful validation `connectTunnel` then `stopTunnel` can stop the old active alias, and DEV catch restores checkpointed bytes without a direct reconnect (`src/setup.ts:442-455,966-971,975-1027`). However, the running launcher monitors readiness and schedules recovery after its failure threshold (`launcher/electron/runtime-supervisor.cjs:1110-1130`), so the first-wave implication that *every* next named chat must reject is too strong. Its narrower gap remains: immediate readiness is not guaranteed following a failed commit, particularly when supervision cannot observe or recovery fails. `src/dev-chat/transport.ts:35-40` checks actual readiness, not the setup result's `tunnelReady: false` (`src/setup.ts:973`), which is intentionally set after validation stops. No outright rejection of the conditional R1 candidate.
- **R1-5-2 repeated, not a new R2 ID.** If message execution throws and either close rejects, the `finally` AggregateError omits the initiating error (`src/dev-chat/cli.ts:421-436`). Both resources are attempted with `Promise.allSettled`, so ordinary successful cleanup and settlement are not being challenged. The loss of primary diagnostic remains limited to the double-failure trigger.

No ownership-safe restoration can be inferred from this review. Automatic capability flags set false during inspection (`src/setup.ts:930-939`) are stored observations, not evidence of a live model failure. Neither a lack of direct CLI IPC nor a false setup-time `tunnelReady` proves absence of launcher recovery or turn settlement.
