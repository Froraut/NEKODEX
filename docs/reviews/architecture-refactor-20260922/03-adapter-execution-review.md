## 03-adapter-execution-F1 — Extract the runtime factory with explicit mode-specific ownership

**Evidence / extension trigger.** `src/adapters/chatgpt-web/index.ts:443–887` contains a roughly 445-line nested runtime factory inside adapter construction. It combines checkpoint preparation, retained-conversation routing, prompt compilation, broker registration, Manual launcher protocol, worker invocation, submission evidence, progress feeds, and cancellation. Automatic read-only and tools paths repeat worker metadata/progress callbacks at `748–777` and `829–857`; Manual and automatic tools branches separately manage deferred token publication, capability retirement and cancellation at `570–745` and `792–884`. Adding a worker lifecycle callback currently requires finding and updating both automatic branches while excluding Manual control where appropriate.

**Concrete change.** Move this factory into `src/adapters/chatgpt-web/turn-runtime.ts`, with a typed constructor context holding already-validated configuration and existing worker/broker/store dependencies. Give its start method a named request object containing parsed execution input, trusted environment, trace identity, capabilities and compaction hooks. Keep distinct Manual, read-only and tools builders; share only the automatic worker lifecycle callback construction and the existing logical/physical cancellation wrapper. Move Manual control types with their implementation and re-export them from `index.ts` for compatibility. Avoid callbacks that reach back into adapter-local mutable state or a generic plugin framework.

**Boundary / callers inspected.** Both ordinary start (`index.ts:1232–1250`) and fresh compaction fallback (`1033–1055`) must use the same factory. The fallback deliberately waits for physical settlement and retains ownership after logical cancellation. Keep its deadline arming and compaction operation ownership in the existing compaction coordinator; extraction must merely forward `onCompactionProgress` and `compactionExecution`. Preserve token publication only after successful compilation, the Manual Sent acknowledgement, terminal success precedence over cleanup failure, `prepared → send_activated → accepted`, and the compaction exception to ordinary submission poisoning. Do not replace `physicalSettlement` with `browser`.

**Benefit.** New runtime callbacks, compilation inputs and mode changes gain one explicit construction boundary, while `index.ts` becomes a coordinator rather than the owner of every transport implementation.

**Write set.** `index.ts`, new `turn-runtime.ts`, optional new `tests/adapter-execution-refactor.test.ts`; all owned by lane 03. No worker, broker, launcher or compaction-handoff implementation edits.

**Smallest verification proposal.** Reuse selected adapter cases for disconnect/reconnect without another submission, ambiguous submission replay, and Manual failure unaffected by self-induced capability retirement (`tests/chatgpt-web-harness.test.ts:1007,1128`; `tests/zero-risk-adapter.test.ts:421`). Add a focused fixture only if existing coverage cannot observe shared callbacks on both automatic modes. Maximum **30 seconds wall time per selected invocation**, 5 seconds per new case; no full harness run.

## 03-adapter-execution-F2 — Give native-round delivery one journal-first contract and one successful-finalization path

**Evidence / extension trigger.** `index.ts:1258–1281` defines local batching/journaling helpers, but delivery, replay, completion and failure policy continue through `1282–1573`. Successful settled replay (`1288–1325`) and live completion (`1407–1451`) independently enforce streamed-text equality, validate structured output, optionally publish its buffered answer, estimate usage, emit completion, complete the journal and clear retry state. Tool replay and fresh tool delivery repeat batch emission/usage at `1336–1349` and `1499–1508`. An output-format or terminal-event change therefore has multiple policy sites, whose ordering is consequential.

**Concrete change.** Extract a private `turn-round-delivery.ts` module with a round delivery object bound to session, round key and observer. Its batch method must append the complete event array before invoking the observer. Give it a single successful-answer method for stream equality, structured validation, buffered output, completion events and journal completion. Supply the effective usage estimator as a narrow closure. Retain explicit orchestration for replay prelude selection, broker revocation, tool-boundary acknowledgement, and browser/error racing in the caller; these have different ordering requirements and should not be hidden inside an all-purpose finish method. Keep retry cleanup immediately after successful delivery, owned by the adapter policy.

**Boundary / callers inspected.** `ChatGptTurnSession.appendRoundEvents` (`turn-execution.ts:486–495`) reserves bytes for the entire batch before append. `roundHasTerminalEvent` and the replay branch prevent duplicate terminal generation after observer interruption. Preserve those contracts, including resource-limit failure delivery outside the full journal (`index.ts:1559–1565`). Keep `submittedTurnFailure` (`327–349`) ahead of retry accounting (`1531–1546`); a new error classification must never reopen an activated/accepted send. Live completion must still revoke before success; settled replay must retain its existing capability-retirement sequencing.

**Benefit.** Output and terminal-event features gain a single completion contract without coupling session ownership to HTTP delivery or weakening no-duplicate-send behavior.

**Write set.** `index.ts`, new `turn-round-delivery.ts`, the same lane-owned regression file. This overlaps F1 and must be implemented by the same owner, not parallel writers.

**Smallest verification proposal.** One controlled browser fixture exercised with completion before observer admission and completion during observation; compare final output, done count and one browser start. Include observer failure midway through a journalled event batch, then exact reconnect. Reuse the existing resource-limit reconnect case (`chatgpt-web-harness.test.ts:4119`). Maximum **30 seconds per focused invocation**, 5 seconds per new case.

## 03-adapter-execution-F3 — Separate session/replay state and feeds from the ownership registry

**Evidence / extension trigger.** `src/adapters/chatgpt-web/turn-execution.ts` is 1,179 lines containing four distinct responsibilities: feeds/runtime shape (`44–191`), identity/key derivation (`193–311`), session serialization and replay accounting (`313–603`), and cross-session ownership/retirement (`605–1179`). Changes to event retention currently share a module with acknowledged launcher release, supersession and native interruption. Trace and text waiter plumbing is duplicated (`54–109`, `111–166`), but their storage/accounting semantics differ.

**Concrete change.** Move feeds and runtime types into `turn-feeds.ts`, and the intact `ChatGptTurnSession` class into `turn-session.ts`. Leave identity derivation and `ChatGptTurnSessions` in `turn-execution.ts` initially, with compatibility re-exports. Keep registry-wide replay admission as the existing injected callback; the session must not import the registry singleton. Preserve separate trace normalization and cumulative text accounting rather than introducing a generic queue abstraction. Do not split the registry's mutually dependent retirement maps in this pass.

**Callers / invariants.** `server.ts` uses the singleton for cancellation and active counts; `compaction-handoff.ts:129–294` consumes session outcome and physical settlement separately. Compatibility exports avoid cross-lane caller edits. Preserve serialization through `tail`, deferred capability retirement (`544–560`), terminal replay-budget poisoning, whole-batch reservation, and retained release obligations until acknowledgement (`827–918`). Registry/session constructors and defaults remain unchanged.

**Benefit / write set.** Separates transport buffering and per-execution replay from cross-execution ownership, enabling future event retention changes without touching the lifecycle controller. Own `turn-execution.ts`, new `turn-feeds.ts`, new `turn-session.ts`; any regression additions use the same lane-owned test file. Single owner across F1–F3.

**Smallest verification proposal.** Select existing journal atomicity/shared allowance cases (`chatgpt-resource-budgets.test.ts:50–94`) and exact-native-interruption case (`turn-broker-lifecycle.test.ts:75`). Maximum **30 seconds per selected invocation**. Parent owns integrated compilation/import validation, builds and UI checks.

## Deliberate non-changes / cross-lane coordination

Keep `concurrency.ts` as the shared startup-capacity contract. Keep `retry-policy.ts` and `retry-continuation.ts` separate: the former bounds attempts; the latter authenticates the exact successor instruction. `server.ts:727–731` records handoff only after a qualifying delivered error, and `environment.ts:227–245` verifies that authority. Combining these stores would blur delivery and execution ownership. `turn-progress.ts` already has a useful reader/recorder/mirror split; preserve its pre-dispatch acknowledgement and worker-owned deadlines, including the explicit absence of a second fixed tool-boundary timer (`index.ts:1385–1400`). No standalone progress rewrite is warranted.

Other lanes may propose changes to worker callbacks, compaction or server delivery; lane 03 owns any necessary wiring inside `index.ts` and `turn-execution.ts`. Parent resolves those interfaces and coordinates selected checks once. No source edits or tests were performed in this review, and no release/provider correctness claim is made.
