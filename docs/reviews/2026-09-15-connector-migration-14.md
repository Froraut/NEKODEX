## Finding

[#487](https://github.com/miuuyy/codex-chatgpt-web/issues/487) remains open, with no comments when checked on 2026-09-15. It reports that Full Harness `codex_exec` drops `sandbox_permissions`, `justification`, and `prefix_rule` while the outer `exec_command` can accept them. The observed `git fetch` and network failures are issue-reported symptoms, not local reproductions.

The gap is explicit in `src/adapters/chatgpt-web/mcp-server.ts:630-637` (the fixed Zod MCP input schema) and `:645-669` (the handler reconstructs only five command fields). `exactTool` at `:120-122` selects an unnamespaced outer `exec_command`, then `shell_command`; `:659-670` calls the selected native tool through the broker, or falls back to the freeform `exec` gateway. Both Full and Manual MCP contracts register this same wrapper with different turn references, so extending its public input changes both cached `tools/list` ABIs. This matches the deliberate identity policy in `docs/architecture.md:73-80` and the prior deferral in `docs/reviews/2026-09-15-upstream-01.md`.

## Boundary and argument risks for the implementing lane

1. Treat the three new fields as **request arguments**, never a local permission grant. The broker carries `wireName`, `freeform`, and `arguments` unchanged (`mcp-server.ts:563-575`; `turn-broker.ts:1138-1168`); the adapter emits them as a native tool call (`src/adapters/chatgpt-web/index.ts:259-271`). Neither wrapper nor broker should approve, retry, change the sandbox policy, or substitute `danger-full-access`. Official [Codex approvals documentation](https://learn.chatgpt.com/docs/agent-approvals-security) places sandbox and approval decisions with Codex; auto-review evaluates actions that already require approval. A forwarded `sandbox_permissions` value requests that lifecycle and does not guarantee approval.
2. Validate shape before forwarding: `sandbox_permissions` should match the **active native schema** enum rather than accepting arbitrary strings; `justification` is a bounded string; `prefix_rule` is an array of bounded strings. Preserve omission as omission. Do not manufacture a justification, approval flag, default escalation, or prefix rule. The MCP Zod schema validates only its own public arguments; `assertBrowserToolArguments` (`mcp-server.ts:198-217`) guards wait-agent timing, not general command schemas. The outer native runtime is the final argument and approval validator.
3. Check the selected command tool's `parameters.properties` before attaching escalation fields. The direct outer schema is preserved from the Responses request (`src/responses/parser.ts:148-159`) into `ChatGptTurnEnvironment.tools` (`codex-rollout-environment.ts:534-612`) and returned verbatim by `codex_tool_inventory` (`mcp-server.ts:838-860`). A future `shell_command` may advertise a different name or no escalation fields: its existing mapping already changes `cmd` to `command` and `yield_time_ms` to `timeout_ms` (`:651-662`). Passing `exec_command` fields to that schema would be an invalid native call. For explicit escalation on a selected tool without the matching native properties, return a clear unsupported-schema error or direct callers to the exact `codex_tool_inventory` + `codex_tool_call` path; do not silently drop the request.
4. The fallback `exec` gateway has **no structured command schema in its catalog**: `gatewayToolCatalogProgram` and `gatewayToolCatalogPage` (`mcp-server.ts:267-330`) retain only nested tool names/descriptions, and inventory marks gateway `parameters` as `additionalProperties: true` (`:872-891`). `execCommandGatewayProgram` (`:436-454`) chooses exactly one nested native command name and passes a JSON-literal argument object. It cannot prove support for escalation fields from that catalog. Fail closed for explicit escalation if exact direct schema evidence is absent, or use the generic exact-tool route when available; never infer support from name or description alone.
5. Keep the generic workaround intact. `codex_tool_call` (`mcp-server.ts:887-957`) requires an exact visible `wire_name`, rejects freeform/structured mixing, and sends supplied structured arguments to the outer tool. It does not duplicate native approval authority. A malformed `arguments` value or unsupported native field may still be rejected by the outer runtime; the wrapper should not claim pre-dispatch full JSON Schema validation that it does not perform. `exactTool` chooses the first matching name without duplicate/schema checks, unlike the stricter `exactCodexAppTool` at `:124-129`; ambiguity deserves explicit handling before escalating.

The current task's exposed `exec_command` declaration includes optional `sandbox_permissions`, `justification`, and `prefix_rule`, but this task has approval policy `never`; it is evidence of one active tool declaration, not proof every host/turn permits escalation. The official documentation describes approval policy behavior, not the exact per-tool field schema. Implementation should derive field support from each current turn's outer registry rather than a fixed global assumption.
