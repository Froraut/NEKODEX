## Phase 1 — new source-evidenced defects

These are distinct from E03/E04/E12 and B06 in the earlier reviews. They are control-flow findings, not reproduced tunnel/account failures.

Count: **3 unique error paths (T01–T03)**. **0 independent optimization findings**. The smaller checksum budget proposed below is part of T01's bounded-read correction, not a separate measured speed improvement.

| ID | Confidence | Trigger, evidence and consequence | Counterevidence / limit |
| --- | --- | --- | --- |
| T01 | High | `src/tunnel.ts:104-114` rejects a declared `Content-Length` over 100 MiB, but a response with absent/understated length is read by `response.arrayBuffer()` in full before checking `bytes.byteLength`. A large/chunked release response can allocate far beyond the stated cap before the rejection. Both asset and checksum fetch use this path at :177-181. | Assets come from a pinned GitHub release and the archive hash is checked before install; this limits ordinary tampering, but neither mechanism bounds peak memory during transfer. No malformed server response was exercised. |
| T02 | High | `src/tunnel.ts:185-189` calls `unzipSync(archive)` without a filter, then searches for one executable. `unzipSync` materializes all entries. A checksum-valid ZIP with many/large unrelated entries can inflate memory beyond the 100 MiB compressed-download limit. | The pinned archive is expected to be small and release-owned; this is resource robustness, not evidence of a current compromised release. Upstream `fflate` explicitly documents a file filter. |
| T03 | Medium | `src/tunnel-service.ts:82-84,157-173` makes `launchctl print` through `runCommand` without a timeout, including each poll of `waitForTunnelServiceUnloaded(20_000)`. If the command stalls, the elapsed-time check cannot execute, so the unload-poll phase can exceed its 20-second deadline. | `launchctl print` normally exits quickly and no stall was observed. The deadline concerns polling after `bootout`, not the whole stop/restart command. |

## Phase 2 — selected changes for later coding runs

1. **T01, bounded download streaming:** count bytes while reading `response.body`, cancel once the cap is exceeded, and keep the timeout active through the read. Retain the `Content-Length` early reject and checksum comparison. Use a small, explicit memory cap for `SHA256SUMS.txt` rather than its archive-sized cap. Focused case later: absent length with bytes crossing the limit should reject before buffering the rest. Complexity: low to medium; no new dependency.
2. **T02, selective ZIP extraction:** use existing `fflate.unzipSync` filter to allow only the exact expected executable entry and impose an uncompressed-size ceiling. Reject duplicate basename matches and malformed archive shapes rather than taking the first entry. Keep version execution and both hashes. Focused case later: an archive with an oversized unrelated entry must not inflate it. Complexity: low to medium; no new dependency.
3. **T03, bounded service probe:** give `launchctl print` a short per-call timeout and preserve the total unload deadline. Surface timeout as a diagnostic instead of silently interpreting it as unloaded. Focused case later: injected stalled command should terminate with a bounded error. Complexity: low, macOS-only path.

This was a priority order during read-only research, not authorization to edit or run tests at that stage. The later instruction authorized **all three findings in correction run 1**; runs 2 and 3 re-review the preceding implementation and direct lifecycle callers. No large suite is needed to decide these cases.
