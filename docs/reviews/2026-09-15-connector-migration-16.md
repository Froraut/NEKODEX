# Connector identity migration: release and installed-client transition (lane 16)

Scope: read-only review of the `d880b12` checkout for coordinated #487 migration. No packaging, CI, updater, account, installation, or version mutation; no tests or typechecks. The parent owns the identity implementation. Published `.1` release notes and metadata remain immutable.

## Version and distribution boundary

- `package.json`, `launcher/package.json`, `src/version.ts`, and the default in `scripts/install.sh` already say `5.2.0-nekodex.2`. The local tag list has `v5.2.0-nekodex.1` and no `.2` tag. A connector ABI change can join the still-unreleased `.2` source; a further source version bump is **not required by the existing release machinery**. Confirm the remote release/tag state before publication. If `.2` has become public or signed elsewhere, use a fresh version/tag and leave its assets immutable. `scripts/publish-release.cjs` expects `docs/releases/${version}.md`; the `.2` release note must describe the new connector names and migration/recovery before any release publication.
- The `.1` macOS release uses the old `Froraut/codex-chatgpt-web` repository identity. Current `.2` source pins `Froraut/NEKODEX` in both package manifests and release/update origin. `docs/release-signing.md` explicitly requires an existing `.1` installation to cross this repository pin with a **manual signed DMG**; redirect or an in-app update cannot satisfy the exact signed metadata/repository check. The earlier Codex Web GPT executable-name transition was also manual. Preserve installed account/profile data and the old app/configuration until the new installation and connector path are proven.
- The transactional updater authenticates exact fork/version/asset metadata, stages and validates the app/runtime, then backs up and replaces installed files. It rolls back files if replacement startup/readiness fails. Its readiness proof covers renderer/browser bootstrap and packaged runtime `--version`, **not** ChatGPT connector creation or a real MCP turn. Its documented rollback excludes account activity and later profile/configuration migrations. Do not use a green updater transaction as the connector-migration receipt.

## Compatible migration order

1. Complete the coordinated source change under the three **new** public identities: Automatic `Codex Native4`, repository DEV `Codex Native4 DEV`, Manual `Codex Zero Risk4`. Keep `Codex Native3`, `Codex Native3 DEV`, and `Codex Zero Risk2` as legacy names alongside older aliases. Include `Codex Zero Risk3` defensively as a legacy alias; it was never published here. Review direct identity callers and public `tools/list` pins together. Since #487 adds fields to `codex_exec`, the existing `Native3`/`Zero Risk2` schema digests cannot describe the new contract.
2. After the parent's focused development verification, prepare `.2` release notes and the normal signed/notarized distribution gates. For an installed `.1` client, perform the required manual signed-DMG repository transition, preserving profile/account files; then launch the matching `.2` app/runtime. A clean install takes the normal installation path. DEV uses its isolated profile and distinct DEV connector.
3. Use launcher **MCP → Connect harness** / runtime setup to persist the new local target before attempting a Full-mode turn. Existing migration policy reuses the mode's tunnel/credentials, keeps Automatic and Manual tunnels distinct, and preserves approval settings. Setup targets a new name but does **not** create or verify a ChatGPT connector. Inspect `releaseVersion` and launcher-owned runtime status: the supervisor rejects a config whose release version differs from the app, and `upgradeManagedRuntime()` runs setup when version or legacy connector migration requires it. Runtime loading must fail closed on a legacy active connector rather than silently selecting it.
4. In the relevant ChatGPT account/workspace, create a **new** connector with the exact mode-specific name and tunnel shown by setup, `Authentication: None`, and intended workspace action permissions. Leave old connector entries untouched for recovery; renaming/refreshing them may keep ChatGPT's cached old schema. Automatic and Manual creation/selection must be handled separately.
5. Run **Verify runtime** for Automatic; explicitly select `Codex Zero Risk4` for Manual. Record connector creation, selection, and one real installed Codex task invoking the changed `codex_exec` schema as separate evidence. One bounded native command that uses an actually supported outer approval field is enough to show forwarding; outer Codex approval remains authoritative. A visible connector or local stdio result alone does not prove ChatGPT loaded the new schema. Do not place approval-field probes or account mutation in this research lane.

## Failure and rollback

- If an update/install fails before local setup, recover the prior app through the updater journal/backup or prior signed installer as appropriate; do not delete the old connector. Read `update-worker.log` and preserve an unfinished journal rather than starting a second update.
- If the new app starts but connector creation/verification/invocation fails, keep the `.2` app and inspect the stage: local target/`releaseVersion`, tunnel, account connector visibility, or outer Codex approval result. Reconnect the harness and create the correct new identity only where that stage warrants it. The file updater cannot roll back these local/account steps.
- If a full rollback to `.1` is necessary **after** `.2` setup, restore a protected copy of the pre-migration local MCP/profile configuration (including `.1` release version and `Native3`/`Zero Risk2` targets) with the prior signed app; merely restoring old app files may leave `.1` facing `Zero Risk4` or a mismatched `releaseVersion`. Keep the original tunnel credentials and old ChatGPT connectors available. Never weaken repository or metadata pins to force an in-app downgrade.
