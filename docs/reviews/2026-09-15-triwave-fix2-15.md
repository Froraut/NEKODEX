# NEKODEX — triwave fix 2, lane 15: tunnel control ownership and cancellation handoff

- **Baseline:** `3740505b0107af9a83053fd523ae1ad30be36465` (`HEAD`)
- **Working-tree context:** reviewed against the existing uncommitted wave1 edits. The requested source scope was limited to `launcher/electron/runtime-supervisor.cjs`; this report is the only new review artifact.
- **ABI boundary:** Native4, Native4DEV, ZeroRisk4 identities and public connector/tool schemas were not changed.

## Changes

### 1. Supervisor-owned tunnel control lifecycle

Added a supervisor-owned tunnel control queue and child registry.

Every `runTunnelCommand` now reserves the next control slot before spawning. The following tunnel control operation cannot spawn until the preceding child has emitted `close`. The exact child remains in `tunnelControlChildren` until that close event, including when the command promise has already rejected after the forced-termination deadline.

This closes the accepted T1-15-1/T2-15-1 ownership gap at the interaction boundary: a timed-out or failed tunnel control operation cannot silently return while a later inventory, connect, stop, or health command starts on top of an unresolved control child. A non-cooperating child therefore blocks later control commands behind an explicit unresolved ownership obligation instead of being forgotten.

### 2. Pipe failures use bounded termination

A tunnel stdout/stderr error now enters the same bounded termination flow as cancellation and timeout:

- retain the pipe failure as the primary diagnostic;
- request normal owned-process-tree termination;
- request forced termination after the existing bounded delay;
- reject after the forced deadline if the child still has not exited;
- keep the child registered and keep the control queue blocked until `close`.

This covers the T2-15-1 entry path without changing the tunnel command contract or output limits.

### 3. Wave1 stale-owner cancellation fix retained

The existing wave1 changes remain intact. `stopStaleOwnedRuntime` passes `startSignal` through tunnel status inspection, the stale tunnel stop command, and stopped-state confirmation. The final cancellation check before state clearing also remains in place. This is the accepted T3-15-1 correction and was not reverted.

## Remaining limits

- No tests, typechecks, scripts, runtime actions, production actions, or commits were run, as requested.
- The correction is source-level. It does not prove behavior against a live non-cooperating tunnel client.
- If a tunnel control child never emits `close`, later tunnel control operations remain deliberately blocked until that ownership obligation settles. This preserves serialization and prevents a second command from racing an unresolved first command; an operator-visible recovery path for a permanently stuck native child remains outside this lane.
- The existing bounded output capture, tunnel alias validation, Native4/Native4DEV/ZeroRisk4 ABI, and public command arguments were preserved.
